# 权限架构说明（现状）

> 依据当前代码整理（分支 `fu-dev`，提交 `b3ec507`）。每个论断都标了源文件与行号，
> 便于逐条核对。**本文件只描述现状，不提出改造方案**；已知缺口集中在 §10。
> 判定矩阵的真机验证结果见 `docs/分组权限测试报告.md`（79 条断言）。

## 1. 一句话：这不是经典 RBAC，而是三条正交轴

代码里没有「角色 → 权限位」的映射表。权限判定由三条互不替代的轴组成，各自有各自的
Actor 形状与判定位置：

| 轴 | 管什么 | 判定在哪 | 权威字段 |
|---|---|---|---|
| **身份 / 角色** | 你是谁、能不能进这道门 | `internal/auth` + `internal/httpapi/middleware.go` | `sessions.role ∈ {admin, user, ''}` |
| **资源归属（分组）** | 这条资源属于谁，你能看 / 能改 / 能管 | `internal/access`（纯函数判定）+ `internal/group`（读库） | `projects/servers/kube_clusters.group_id` + `resource_groups.visibility` |
| **凭据分级** | 一把密钥谁能列、谁能读明文、是否还可用 | `internal/vault/rbac.go` + `internal/vault/vault.go` | `credentials.scope / owner_id / enabled` |

**两条轴上的 "admin" 不是同一种东西，nil 的语义也刻意相反**（这是最容易串用的地方，
两边源码都写了注释）：

- `access.Actor`：缺 session 一律 fail closed → `ErrUnauthenticated`（`internal/access/access.go:127`）。
  注释明说「绝不能退化成 nil = 系统调用 = 放行」（`internal/httpapi/access_guard.go:24-27`）。
- `vault.Actor`：`nil` 视为系统调用 = admin（`internal/vault/rbac.go:14-32`），因为 vault 面向领域内
  调用（health check、流水线取凭据等），那时没有"当前登录用户"。

角色只有两档（`internal/auth/rbac.go:33-38`、`internal/users/users.go:39-43`）：`admin` / `user`，
外加旧部署兼容值 `''`（见 §6）。

## 2. 用户 ↔ 角色 ↔ 分组 的关联链

这是本架构最容易讲错的环节，按数据流写实：

```
users (id UUIDv4, username UNIQUE, role, enabled)
  │  role 决定「身份轴」档位；admin 在 users 表有一行固定 UUID
  │  = users.BootstrapAdminRegularUserID = 00000000-0000-0000-0000-000000000001
  │    （internal/users/users.go:30-38，invariant 测试 internal/users/consts_test.go；
  │      改动会让所有已签发 admin personal 凭据的归属错位）
  │
  ├── sessions.user_id / sessions.role（迁移 `internal/store/migrations/sqlite/0053_session_user_binding.sql:31-32`）
  │     └── 登录时快照进会话：admin 登录 → 上面那个固定 UUID + role="admin"；
  │         普通用户登录 → 该用户 id + role="user"（internal/auth/session.go:33-42）
  │         注意 role 是**会话里的快照**，不是每次请求 join users 表 —— 这直接导致
  │         §10 里「禁用账号不立刻失效」的现状。
  │
  ├── resource_groups.owner_id ── 组长（一个用户）
  │     └── 组长不写进名册表：resource_group_members 只存成员，
  │         「组长身份来自 resource_groups.owner_id，避免两处真相」（迁移 0055 头部注释:3）
  │
  ├── resource_group_members (group_id, user_id) 复合主键去重，
  │     group_id → resource_groups ON DELETE CASCADE（迁移 0055:8-15）
  │
  ├── credentials.owner_id ── personal 凭据的归属（迁移 0058_credential_owner.sql）
  │
  └── 资源侧：projects.group_id / servers.group_id / kube_clusters.group_id
        （迁移 0056:8 / 0057:6 / 0059:18；'' = 未归组）
        runs 表**没有** group_id：运行随项目走，
        归属解析由 Repository 内部做 run → project → group 两跳（internal/access/access.go:48-49）
```

所以「用户属于分组」这件事在库里是**两条独立关系**：`resource_group_members.user_id`（名册成员）
和 `resource_groups.owner_id`（组长）。判定优先级上组长更宽（见 §4）。

`users` 与 `admin_user` 的关系：`admin_user` 是单行表（id=1）承载首任管理员的口令，
`users.role='admin'` 的行是同一实体的 users 视角，两者由 `BootstrapAdminRow` /
`SyncAdminPasswordChange` 保持同步（`internal/users/users.go:8-16`）。

## 3. 一个请求依次经过什么

```
全局：chi Recoverer                          internal/httpapi/router.go:463
      localeMiddleware（本地化错误消息）      internal/httpapi/router.go:466

公开面（不鉴权，靠各自签名）：
  /api/webhooks/{token}   签名校验            internal/httpapi/router.go:486
  /approvals, /approvals/act  HMAC token      internal/httpapi/router.go:491-492
    GET 只渲染确认页、无副作用（防 IM 预取自动放行）；POST 才解析门

/api 组：
  1 requireAuth(svc)        cookie → Verify → 注入 Session     internal/httpapi/router.go:496-498 → middleware.go:30
  2 requireCSRF             写方法比 X-CSRF-Token              internal/httpapi/router.go:499-501 → middleware.go:67
  3 accessGuardMiddleware   按 URL 认资源 + 定档                internal/httpapi/router.go:503     → access_guard.go:75
  4 子组档位                RequireAdmin / RequireUser          middleware.go:99 / :118
  5 handler 内补判          Manage 档、终端与 /fs* 的 Operate 档

审计不是中间件：handler 在业务成功后显式 recordAudit（internal/httpapi/router.go:507 起逐个传入 aud）。
```

`accessGuardMiddleware` 的存在理由写在 `internal/httpapi/access_guard.go:5-11`：
`/api/projects/{id}/*` 与 `/api/runs/{id}/*` 合计三十多条路由，分散判定必然漏
（漏一条就是一个越权口子），所以按 URL 形态一次性收口，**新增路由自动被覆盖**。

它只认四种资源（`access_guard.go:52-67`）：`projects` / `runs` / `servers` / `kube-clusters`。
明确豁免的字面段：`projects/test-clone`（没有既成资源可判）、`servers/metrics` 与
`servers/containers`（聚合总览走「整表按可见范围过滤」，见 §7）。
`POST /api/projects`（创建）同样不归它管。

**档位映射只有一条规则**：`GET/HEAD/OPTIONS → ActView`，其余方法 → `ActOperate`
（`access_guard.go:91-96`）。

`svc == nil`（未装配权限仓储）时中间件直接透传（`access_guard.go:76-78`），
让单机演示与既有测试不受影响；生产装配恒定注入
`groupSvc := group.New(st.DB)` + `accessSvc := access.NewService(groupSvc)`
（`cmd/pipewright/main.go:120-122`）—— **同一个实例既当 `/api/groups` 的领域服务，
又当 `access.Repository`**，避免同一份名册两处缓存。

## 4. 归属轴的核心：`Decide` 的短路顺序

`internal/access/access.go:126-148`，按顺序命中即返回：

| # | 条件 | 结果 |
|---|---|---|
| 1 | `actor == nil \|\| actor.UserID == ""` | `ErrUnauthenticated` → 401 |
| 2 | `actor.IsAdmin()` | 放行 |
| 3 | `g != nil && g.OwnerID == actor.UserID` | 放行（**组长在组内拥有一切**，含改名册、把资源甩出组） |
| 4 | `act == ActManage` | 拒绝（未归组与公开分组没有「归属」可管，只有管理员能改） |
| 5 | `g.IsPublic()`（含 `g == nil` = 未归组） | 放行 |
| 6 | `g.HasMember(actor.UserID)` | 放行 |
| 7 | 其余 | `ErrForbidden` → 403 |

三态语义（`access.go:7-9`、`internal/group/group.go:11-19`、迁移 0054 头部注释）：

| 归属 | 可见 / 可操作 | 谁能管归属（Manage） |
|---|---|---|
| **未归组** `group_id=''` | 全员可见可操作（存量数据全在这一态，不迁移） | 仅管理员 |
| **public 分组** | 同上 | 管理员 + 组长 |
| **private 分组** | 组长 + 名册成员 + 管理员；其余 403 | 管理员 + 组长 |

`Act` 三档（`access.go:52-59`，数值越大越重）：`ActView` 看得见（列表/详情/日志/报告）、
`ActOperate` 改得动（编辑/删除/触发运行/审批/部署/SSH 执行）、`ActManage` 管归属
（归组改组、私有分组成员名册）。

两处 **fail closed**，是这套设计里最重要的防守：

1. **悬挂引用**：资源的 `group_id` 指向已删的分组 → 按最私有一档处理
   （`access.go:193-197` 把快照替换成 `Visibility: private`），报 403 `group_missing`
   而不是「查不到组 = 放行」。错误映射见 `access_guard.go:106-123`，其中
   **404 判定刻意排在 403 之前**，否则「项目不存在」会被伪装成无权限。
2. **仓储未装配**：`Service.Can` 在 `s.repo == nil` 时只放 admin，普通用户一律拒
   （`access.go:178-184`）。

另外 `ErrForbidden` 选择明确回 403 而不是伪装 404，理由写在 `access.go:79-80`：
分组是协作资源，让人知道「资源存在但不属于我」比隐身更符合产品预期（用户据此去申请加入）。

## 5. 三条必须 handler 显式补判的例外

「读→View / 写→Operate」这条规则覆盖不到的，代码里都单独开了入口：

| 例外 | 为什么要补 | 位置 |
|---|---|---|
| **终端 / 远程文件：GET 也按 Operate** | WS 升级后无法回写 HTTP 状态码，必须在握手前挡下；「在目标机上跑任意命令」语义上是操作。`/fs*` 全是读写混合，列表 GET 也算操作 | `access_guard.go:124-142 requireTerminalOperate`；调用于 `container_terminal.go:122`（容器 WS）、`:222`（主机 shell WS）、`fs_upload.go:378-394 requireFSAccess`（被上传/文件各端点共用） |
| **ActManage：归属级动作** | 中间件规则里没有 Manage 档；且归组要判**新旧两侧** | `access_guard.go:157-173 requireResourceManage` → `servers.go:230`（改归属，旧侧）、`:281`（删主机）、`kube_clusters.go:197,246`；`access.go:215 CanGroup` 判新侧 → `projects.go:135-155 requireGroupPlacement`（用于创建 :177 与 PATCH）、`servers.go:132 requireServerPlacement` |
| **admin 档：与分组无关的全局设置** | 分组判定管不到"设置类"动作 | `RequireAdmin`：`GET /api/audit`（`internal/httpapi/router.go:516`）、`POST /api/credentials/{id}/reveal`（`:527`）、`/api/admin/*` 整棵子树（`:532-573`：build-envs、config-profiles、users CRUD、凭据启停）、`POST /api/groups` + `DELETE /api/groups/{id}`（`:593-595`） |

两条产品决定值得单独记：

- **登记一台未归组主机 = 向全员开放一个可 SSH 的目标**，所以新建未归组服务器收在管理员
  （`servers.go:127-141` 注释与 `requireServerPlacement`）；组长只能在**自己的组里**加机器。
  改归属（PUT）则两侧都要管得住：旧侧 `requireResourceManage` + 新侧 `requireGroupPlacement`
  （`servers.go:196-240`）。
- **更换组长只有管理员能做，组长本人说了不算**（`groups.go:291-295`）——
  换组长是权限边界改动，不能让既有边界内的人自授。
  分组的建/删是 admin-only，改名 / 描述 / 可见性 / 名册是 admin 或组长
  （`groups.go:276`、`:347` 走 `loadGroupForActor(..., access.ActManage)`）。

## 6. 身份轴细节

- **会话**：`sessions(token, csrf_token, user_id, role, created_at, expires_at, last_seen_at)`。
  token 与 CSRF 各 32 随机字节（64 hex）。TTL 7 天 + **滑动续期**，但只在距上次 `last_seen`
  超过 60s 才写库，避免每请求一次 UPDATE 的写放大（`internal/auth/session.go:11-22`）。
- **旧会话兼容**：`role=''` 在 `RequireAdmin` 里**按 admin 放行**
  （`internal/auth/rbac.go:40-47`、`Session.IsAdmin` `internal/auth/session.go:45-52`），
  注释写明理由是「避免升级锁死旧部署的管理员」。这类会话要登出重登一次才带上明确 Role。
- **登录**：先查 `admin_user` 单行、再查 `users` 表两条路径（`internal/auth/service.go:156-181`）。
  两个反枚举设计：用户名用 `subtle.ConstantTimeCompare` 恒定时间比较；用户不存在时仍跑一次
  argon2id（`dummyHash`，`service.go:48-56`）。`dummyHash` **必须是静态常量**——在 `init()` 里现算
  会让进程空载常驻内存永久抬高 ~64MB（实测 18MB→82MB），逼近 NFR-4 的 ≤100MB 红线。
- **锁定**：连续失败 5 次 → 锁 15 分钟（`internal/auth/lockout.go:8-12`）。
  当前是**内存计数器**（进程重启清零）、单管理员实例的全局单一计数、不按 IP/用户分桶
  （`lockout.go:24-27` 自注为后续可选扩展）。
- **口令规则**：新口令至少 8 位（`service.go:33-36`）；改口令要校验当前口令
  （`ErrInvalidCurrentPassword`）。**首登强制改密未实现**（独立 story）。
- **普通用户端点**：`RequireUser` 接受 admin 与 user（`internal/auth/rbac.go:49-55`），未登录 401。
  挂在 `/api/build-envs`、`/api/build-envs/languages`、`/api/config-profiles`（只读已启用项）
  与 `/api/groups*` 的读侧（`internal/httpapi/router.go:576-592`）。

## 7. 列表的可见范围：不逐条判定，改成集合作为条件

逐条 `Can` 在列表场景是 N 次查库，所以列表走另一条路：

- `access.go:251-267 VisibleGroups(actor)` → admin 直接 `ListFilter{Unrestricted: true}`（不查库）；
  普通用户拿「所有 public 组 + 自己作为组长或成员的 private 组」，并且
  **固定把 `Ungrouped('')` 放进白名单首位**（`access.go:265-266`）——否则存量未归组资源
  会凭空从列表里消失。
- `access.go:271-289 ListFilter.Clause(column)` 编译成 `column IN (?,?)`；
  `Unrestricted` 返回空串让调用方跳过条件；`GroupIDs` 为空也**仍生成条件**
  （`column = ''`），注释明说「不能退化成无条件放行」。
- 六个入口在用：`projects.go:106`、`runs.go:203`、`servers.go:92`、
  `server_metrics.go:953`（`GET /api/servers/metrics` 聚合）、
  `server_containers.go:240`（容器总览聚合）、`kube_clusters.go:87`。
  领域层把过滤作为入参接收：`project.Service.List(ctx, visible)`（`internal/project/project.go:156-159`）、
  `target` / `kube` / `run` 的 `Filter.Visible access.ListFilter`（`internal/target/target.go:108`、
  `internal/kube/kube.go:85`、`internal/run/run.go:231-232`），
  且各自的非 Scoped 版本显式传 `Unrestricted: true`，避免默认值把已归组数据静默藏掉。

MySQL 方言下这条 `IN` 拼接由 `internal/storetest` 覆盖（需要 `PIPEWRIGHT_TEST_MYSQL_DSN`，
见 `docs/MANUAL-VERIFICATION.md`）。

## 8. 凭据分级轴

- `internal/vault/rbac.go:40-62 effectiveFilter(actor, requested)`：admin / nil → 请求什么给什么；
  普通用户 → **强制把 `OwnerID` 覆写成自己**（忽略调用方传的别人的 id），
  视角 = 共享凭据 ∪ 自己的 personal。
- `vault.go:606-630 ListWithActor`：共享的 `scope <> 'personal'` 与自己的 personal
  **必须写在同一条 SQL 里**，否则「both + owner」会被误当成不过滤 owner 而泄漏他人 personal。
  用 `scope <> 'personal'` 而非 `= 'global'`：0058 之前建的老凭据 `scope` 是空串，
  等值判定会让它们在列表里凭空消失。
- **为什么 global 凭据不对普通用户隐藏**（`internal/vault/rbac.go:45-49` 整段注释）：存量部署的凭据
  **全是** global，项目/服务器配置都引用它们，藏起来会让非管理员的项目页显示成「未选择凭据」
  并无法再选回来——那不是收紧权限，是把老数据打死。列表只出掩码，引用不到明文；
  写 / 删 / 读明文仍有独立的门。
- 读明文：`GetWithActor` / `RevealWithActor` 都先 `authorizeRead`
  （`vault.go:659-686`；global 且非 admin → `ErrAccessDenied`，personal 且 owner 不匹配 → 同）。
  HTTP 层再收一层：`POST /api/credentials/{id}/reveal` 挂 `RequireAdmin`（`internal/httpapi/router.go:521-527`），
  即**本期连所有者本人都不能 reveal 自己的明文**，只能删了重建。
- 启停：`DisableWithActor` / `EnableWithActor` 要求 admin 且凭据 `scope='personal'`
  （`vault.go:700-727`），禁用只改 `enabled` 元数据、密文留着，但取用路径立刻报
  `ErrDisabledCredential`——这正是「立刻停用一把可疑令牌」的效果。
- 创建 `scope='personal'` 却不给 `owner_id` → `ErrOwnerRequired`（`internal/vault/rbac.go:66-68`）：
  没有归属的个人凭据等于没人能看见，入参阶段直接拒，而不是静默落成 global。

## 9. 前端只做展示，权威全在服务端

- 角色来源：`web/src/stores/session.ts` 从 `GET /api/auth/session` 拿
  `SessionUser = {username, role}`（`session.ts:11` 注释 + `:45-59` 缓存逻辑；
  401 = 未登录，5xx/网络错 = 保持原状态并置 `isNetworkError`，避免把已登录用户踢到登录页）。
- 路由级：`meta.adminOnly` 对非 admin 重定向到 dashboard（`web/src/router/index.ts:218-222`），
  注释写明「后端 RequireAdmin 中间件是权威校验，这里提前拦是为了不渲染注定 403 的页面」。
- 菜单级：`web/src/layouts/AppShell.vue:99-108` 的 `navItems` 带 `adminOnly` 标记，
  `visibleNavItems` 按 `role === 'admin'` 过滤。**分组页刻意不是 adminOnly**（`AppShell.vue:102-103`
  注释：组长也要进得来）。`web/src/views/Settings.vue:21,51` 同口径。
- 控件级：**不由前端推断权限**，后端在 DTO 上直接打 `canManage`
  （`internal/httpapi/groups.go:148` 用 `access.Decide(actor, g.Snapshot(), ActManage)` 现算），
  界面只 `:disabled="!g.canManage"` + 悬浮提示（`web/src/views/Groups.vue:286-287`），
  项目与集群侧同理（`web/src/views/Projects.vue:107-138`、
  `web/src/views/settings/SettingsServers.vue:46-68`、`SettingsKubeClusters.vue:46-58`）。

## 10. 已知缺口与风险（本期只记录，不改行为）

按「影响面 / 是否有意为之」分两类。

### 10.1 唯一的非对称收口（看起来是漏收，非取舍）

**删除项目只判到 Operate，没有像删主机 / 删集群那样补 Manage。**
`makeDeleteProjectHandler`（`internal/httpapi/projects.go:286` 起）直接 `svc.Delete`，
归属判定全靠 `/api` 组中间件，而中间件规则是「GET → View，其余 → Operate」。后果：
**私有分组的普通成员也能删掉组内任意项目**。对照删主机（`servers.go:273-281`）与
删集群（`kube_clusters.go:197,246`）都显式补了 `ActManage`，理由是「删除是归属级动作」。

真机矩阵 C 段没有「成员删项目被 403」这条断言——因为实现就是放行，断言会与实现互相印证而失效。
收紧方式：`makeDeleteProjectHandler` 补一行 `requireResourceManage(w, r, acc, access.KindProject, id)`
+ 一条 403 断言。**决定：本期不动**（会改变私有组成员的既有能力，属产品决定）。

### 10.2 有意的取舍（源码注释里都写了理由）

1. **禁用账号与重置口令都不撤销已签发会话**：`role` / `enabled` 是登录时快照进 `sessions` 的，
   禁用后旧浏览器仍能继续操作，只挡新登录（`docs/分组权限测试报告.md` §7.1，H3 断言记录现状）。
   要「禁用 = 立刻失效」需要一张会话撤销表。
2. **旧会话 `role=''` 按 admin 放行**：为不锁死升级前的管理员（`internal/auth/rbac.go:40-47`）。
3. **未归组资源对全员开放写**（含改内容），只有归属收在管理员手里——
   存量数据不迁移，升级当天不能把别人的项目变成"谁都看不了"。代价：想保护一个项目必须显式建组并归组。
4. **reveal 明文只开放给管理员**，所有者本人也不能读自己的明文。
5. **登录失败计数是内存的、单管理员全局一份**：重启清零、不分 IP（`internal/auth/lockout.go:24-27`）。
6. **首登强制改密未实现**。

### 10.3 文档与代码的小漂移（顺带记）

`internal/store/migrations/sqlite/0054_resource_groups.sql` 头部注释列了 `updated_by` 列
「最后一次改动者 users.id，仅审计用途」，但 `CREATE TABLE resource_groups` 里**没有这一列**
（只有 `created_by` / `created_at` / `updated_at`）。读注释时别当成有。

## 11. 加判定 / 加用例的正确姿势

- 判定规则**只写在 `internal/access.Decide` 一处**（`access.go:123-148`）。
  需要新档位或新 kind，先改纯函数 + 表驱动单测（不碰库，三态矩阵可穷举），
  再动 `Repository` 读路径。
- 新增 `/api/{projects|runs|servers|kube-clusters}/{id}/*` 路由**自动被中间件覆盖**，
  不要在各 handler 里重复判 View/Operate；只有 Manage 档、以及"GET 但语义是操作"的通道
  才需要显式补判。
- 加真机用例：先在 `internal/access` 的表驱动单测补全判定矩阵，再在
  `scripts/perm-matrix.py` 加一条真机断言，然后 `python3 scripts/perm-report.py` 重生成报告
  （流程与夹具见 `docs/分组权限测试报告.md` §8）。
- 未覆盖项及它们各自的替代验证位置，列在 `docs/分组权限测试报告.md` §6
  （WS 终端握手、悬挂引用、MySQL 方言、并发竞态）。
