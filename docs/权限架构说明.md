## 1. 一句话：三条正交轴，一次判定取更严的一档

权限判定由三条互不替代的轴组成，各自有各自的 Actor 形状与判定位置：

| 轴 | 管什么 | 判定在哪 | 权威字段 / 表 |
|---|---|---|---|
| **角色（功能轴）** | 这类动作你**允不允许做**（与数据归属无关） | `internal/access/perms.go`（内置模板点集）+ `catalog.go`（自定义角色缓存）给出点集 → `roles.go` 的 `Ceiling` 由点集派生 + 在 `Service.Can` 里前置执行 | `sessions.role` × 点集：内置档在 `permDict` → `rolePerms`（`perms.go:48-82`、`:95-122`），自定义档在 `roles` / `role_perms` 两张表（迁移 0062） |
| **资源归属（数据轴 / 分组）** | 这条资源属于谁，你能看 / 能改 / 能管 | `internal/access`（`Decide` 纯函数）+ `internal/group`（读库） | `projects/servers/kube_clusters.group_id` + `resource_groups.visibility` + 名册 |
| **凭据分级** | 一把密钥谁能列、谁能读明文、是否还可用 | `internal/vault/rbac.go` + `internal/vault/vault.go` | `credentials.scope / owner_id / enabled` |

功能轴是后加的（原设计只有后两条轴 + 一个 `admin`/`user` 布尔档）。**有效权限 =
min(角色上限, 分组授予)**，落点在 `Service.Can`：先查表封顶，再查库解析归属
（`internal/access/access.go:182-189` 功能轴 → `:197-212` 数据轴）。顺序是刻意的——
角色注定不允许的动作不必去库里解析归属，省一次读。

两个边界要说清：

- **`ActManage` 不受角色上限约束**（`roles.go:11-13`、`access.go:184`）。Manage 判的是
  「谁拥有这份数据」本身（改归属、删资源），组长靠它管自己的组；若让角色封掉 Manage，
  新建角色会静默夺走组长的既有管理权——那是数据轴的事，不该由功能轴越权。
- **角色一律只收窄不放宽**：内置 `user` 对四类资源都是 `ActOperate`，与引入本表之前的
  行为逐字一致（`roles.go:15-16`；点集即「全字典去掉设置点」`perms.go:100`），所以存量账号升级当天权限不变。

**两条轴上的 "admin" 不是同一种东西，nil 的语义也刻意相反**（最容易串用的地方，
两边源码都写了注释）：

- `access.Actor`：缺 session 一律 fail closed → `ErrUnauthenticated`（`access.go:131-133`）。
  注释明说「绝不能退化成 nil = 系统调用 = 放行——那是 vault 包的约定」
  （`internal/httpapi/access_guard.go:26-27`）。
- `vault.Actor`：`nil` 视为系统调用 = admin（`internal/vault/rbac.go:13-31`），因为 vault 面向
  领域内调用（health check、流水线取凭据等），那时没有「当前登录用户」。

角色取值有三类（权威定义 `internal/access/roles.go:23-34` 只管第一类，展示顺序 `Roles()` `:36-39`）：
①内置五档 `admin` / `user` / `developer` / `ops` / `viewer`（代码表，当模板）；②任意多个**自定义角色**，
`users.role` 存它们的 `roles.id`（uuid v4），见 §2.5；③旧会话的 `''`（见 §7）。
`internal/users/users.go:41-44` 与 `internal/auth/rbac.go:35-40` 里的角色常量只是别名或残留，
**新增角色不再需要改代码**：在「用户与权限 → 角色」建一条即可，`RequireUser`、`SetRole`、
能力位下发全按「先查代码表、再查自定义缓存」判（`ValidRole` `perms.go:169-175` → `pointsFor`
`catalog.go:96-109`；`rbac.go` 那两个常量已无人引用，见 §11.3）。

## 2. 功能轴：角色 → 功能点 → 各类资源的最高档位

### 2.1 为什么在「类别 × 档位」之外再加一层点

四类资源只有 12 格上限，而左栏是十几条具体入口：服务器状态、容器总览、证书大盘、预览环境、
异常检测都算 `KindServer`。按类别开关只能整块亮或整块灭，表达不了「运维要看主机指标，
但复用库不必给他」这种单条差异。功能点（`internal/access/perms.go:28-36`）补的就是这层粒度。

点**按能力命名、不按菜单位置命名**（`container.operate`，不是 `nav.containers`）：入口改名、
页面合并都不该改动权限语义，所以 ID 里不出现路由路径（`perms.go:29-30`）。

一张表两用，不养第二套判据（`perms.go:7-10`）：

- **菜单 / 路由**：点集随会话回在 `Capabilities.Perms`，前端据此决定入口出不出得来。
- **请求上限**：`Ceiling` 由同一张点集算出来，所以「入口亮了」与「这个写请求 403」不可能各说一套。

### 2.2 点字典（`perms.go:48-82`，21 个点）

| 点 ID | 类别 | 需要的档 | 亮起来的是哪一处 |
|---|---|---|---|
| `dashboard.view` | project | view | 概览 |
| `project.view` / `project.edit` | project | view / operate | 项目列表；改项目配置、流水线编排、触发器 |
| `library.view` / `library.edit` | project | view / operate | 复用库；含自定义节点工作室（模板与变量组的增删改同档，不另开点） |
| `run.view` / `run.operate` | run | view / operate | 运行与运行详情；审批 / 重试 / 取消 |
| `environments.view` | run | view | 环境（按环境聚合的部署历史 + 回滚入口） |
| `metrics.dora.view` | run | view | DORA 指标 |
| `server.view` / `server.exec` | server | view / operate | 服务器状态；主机终端 + 远程文件（坐到那台机器前面是同一件事，不拆两点） |
| `container.view` / `container.operate` | server | view / operate | 容器总览；生命周期与镜像清理同档（能重启就该能删悬空镜像） |
| `cert.view` | server | view | 证书总览 |
| `preview.view` / `preview.recycle` | server | view / operate | 预览环境；手动回收 |
| `anomaly.view` / `anomaly.edit` | server | view / operate | 异常检测；改检测规则 |
| `cluster.view` / `cluster.operate` | kube_cluster | view / operate | K8s 集群；发布 / 回滚 |
| `settings.access` | **platform** | view | 设置那一组（全局凭据 / 保险库 / 审计 / 通知 / AI / DNS / 系统信息 / 服务器与集群登记） |

两点口径要说清：

- **`Act` 刻意不到 manage**（`perms.go:20-22`）：manage 判的是「谁拥有这份数据」，归数据轴管。
  让功能点能封住 manage，等于改一次菜单顺带夺走组长的既有管理权。
- **`Platform` 类别（`perms.go:40`）不在 `ResourceKinds()` 里**，因此永远不会是 `Can` 的入参；
  派生上限时它被跳过（`roles.go:77-87` 只比 `p.Kind == kind`），只由设置位这一条线兜。设置组本期不逐页拆点——
  这些端点本来就统一收在 `RequireAdmin` 后面，拆了只会多出一堆「要么全给要么全不给」的伪粒度
  （`perms.go:42-44`）。

### 2.3 内置模板 → 点集（`perms.go:95-122`）

这张表是**模板**：五档内置角色的点集写在代码里、不进库，页面上只读、可复制成自定义角色（§2.5）。
名单按「这个角色是做什么的」写，不从档位反推——反推出来的表只能复述今天，加不了粒度。

| 点 | `admin` | `user` | `developer` | `ops` | `viewer` |
|---|:-:|:-:|:-:|:-:|:-:|
| dashboard.view / project.view / library.view / run.view / environments.view / metrics.dora.view / server.view / container.view / cert.view / preview.view / anomaly.view / cluster.view | ✓ | ✓ | ✓ | ✓ | ✓ |
| project.edit / library.edit | ✓ | ✓ | ✓ | — | — |
| run.operate | ✓ | ✓ | ✓ | ✓ | — |
| server.exec / container.operate / preview.recycle / anomaly.edit / cluster.operate | ✓ | ✓ | — | ✓ | — |
| settings.access | ✓ | — | — | — | — |

生成规则（不是手抄五遍）：`admin` = 全字典（`:97`）；`user` = 全字典去掉设置点（`:100`）；
`developer` / `ops` 按名字逐条列（`:104-120`）；`viewer` = 字典里所有「非平台且 `Act == view`」
的点（`:121`，由 `permsWhere` 筛，漏项就是少一个入口，所以不手抄）。

读法：

- `developer` 能改项目、能跑流水线；落点那五个入口（主机状态 / 容器 / 证书 / 预览 / 异常检测）
  他**看得到状态但一个操作按钮都不给**——排障要看主机指标与容器列表，不该因此给他终端。
  这就是点比类别细的那一档。
- `ops` 能操作落点、能对**既有运行**做审批 / 部署 / 重试 / 回滚，但不改项目配置、不进复用库编辑。
  注意：手动触发一条流水线走 `POST /api/projects/{id}/runs`，按 URL 属于 **project** 档，
  所以 **`ops` 不含「发起构建」**（`roles.go:28-30` 自注；要放开得把 Kind 拆细，留到后续）。
- `viewer` 只读：12 个 view 点全给，任何 operate 点与写请求都没有（写请求由上限 403，见 §4）。

### 2.4 档位是派生出来的，不是第二张表

`Ceiling(role, kind)`（`roles.go:66-92`）取该角色点集里属于这个类别的点的最高 `Act`；
点集由 `pointsFor`（`catalog.go:96-109`）给出，**先查代码表（内置模板）、再查自定义角色缓存**：

- 未知类别（不在 `ResourceKinds()`）→ `ActView`（`:67-69`）；
- `role == ''`（旧会话）或 `admin` → `ActManage`（`:70-72`，与 `Session.IsAdmin` 同口径，
  否则升级当天旧管理员会话被静默降成只读）；
- 认不出的角色（内置没有、库里也没有）、或一个点都没落到这个类别 → `ActView`（`:73-76`、`:88-90`，
  fail closed：认不出的东西先只让看）。

`SettingsAllowed(role)`（`roles.go:96`）= `HasPerm(role, "settings.access")`，
`RequireAdmin` 中间件读的就是它（`internal/httpapi/middleware.go:104-117`，判据在 `:111`）。
以前这层读 `Session.IsAdmin`，与前端菜单是两套判据并排写；今天两者取值仍完全等价，
但同源之后不会出现「某天给新角色开了设置点，页面进得去而端点全 403」。
注意：**自定义角色永远拿不到那个点**（§2.5 的硬边界），所以「给某角色开设置页」仍是改代码那一行。

`HasPerm` / `PermsFor`（`perms.go:177-188`、`:190-209`）：空串按管理员口径给全字典，
未知角色给空集（前端据此把所有挂门入口收起）；`PermsFor` 回传前按字典过滤一遍，
手抄错一个 ID 不会让前端拿到一个谁也不认的字符串。

改点集 = 改上限，所以存量账号一格不许漂：`TestCeilingMatrixUnchanged`
（`internal/access/perms_test.go:53`）把改动前的 5 角色 × 4 类别矩阵连 `''` 与认不出的
`root` 一起钉死。另外 `perms_test.go` 还钉了字典自洽（`:15`，ID 不重、不含 `/`、
`Act` 不到 manage、`*.view` 命名一致）、角色引用的是已知点（`:42`）、
序列化形状（`:73`）、以及这一整层存在的理由——`TestRoleMenuGranularity`（`:112`）
断言 developer 拿到主机侧五个只读点但一个操作点都不给、ops 有 `container.operate`
却没有 `project.edit` / `library.edit`。

三个入口函数：

- `Ceiling(role, kind)`（`roles.go:66-92`）：**未知角色 / 未知类别 → `ActView`**（fail closed，
  认不出的东西先只让看）；`role == ''` 按 `admin` 处理（`:70-72`，见上）。
- `NormalizeRole(role)`（`:45-59`）：未知名归到 `user`，但**空串保留为空**——空串是旧会话取值，
  语义是「按管理员」，改写成 `user` 就是降权。报错信息与审计用它（`access.go:187`）。
  注释明写它**只供展示与报错**，别接进判定：它认不出自定义角色 id 时会退成 `user`，
  那是「读起来顺」而不是「权限够」（`roles.go:48-50`）。
- `ValidRole(role)`（`perms.go:169-175`）：是否为可用角色（不含空串），判据是 `pointsFor`
  ——内置键集**加上已装载的自定义角色**。写库侧的校验用它：`RequireUser` 中间件
  （`internal/auth/rbac.go:56-58`）与 `users.SetRole`（`internal/users/users.go:301-305`）
  都按这张表判，所以不会出现「库里有这个角色、但所有 `RequireUser` 端点都 401」的漏收。

`Create` 时传了个认不出的角色名不会报错，而是**静默按 `user` 落库**
（`internal/users/users.go:240-243`）；改角色走 `SetRole`，那里才是严格校验（`:301-305`）。

### 2.5 自定义角色：内置档降级成模板，点集进库

这是 P4 带来的结构性变化——功能轴的权威从「一张代码表」变成「代码表 + 两张库表」，
所以判定入口的读法也跟着分成两级。

**存储**（迁移 `internal/store/migrations/sqlite/0062_roles.sql:16-31`，mysql 同构）：

| 表 | 列 | 说明 |
|---|---|---|
| `roles` | `id`（uuid v4，PK）、`name`（`NOT NULL UNIQUE`）、`description`、`base_role`、`created_by`、`created_at`、`updated_at` | 只存**自定义**角色；`base_role` 记复制来源的内置名，仅用于页面提示，无判定语义 |
| `role_perms` | `(role_id, perm_id)` 复合主键，`role_id → roles ON DELETE CASCADE` | 一个角色一行一个点；`perm_id` **不加外键**——点的权威在代码字典里，删了点由装载时清理（`:13-14` 注释） |

内置五档**不落库**（`:1-7` 头部注释给了两条理由）：①升级时新加的功能点自动跟着内置档位走，
不会被各实例库里的历史手改拖住；②内置 `admin` 改不掉也删不掉，是一条防自锁兜底。

**读侧**（`internal/access/catalog.go`）：`CustomRole` `:26-31`、`RoleStore` 窄接口 `:33-36`、
`roleCatalog`（`RWMutex` + 整批替换的快照）`:38-44`、`SetRoleStore` `:48-55`、
`ReloadRoles` `:57-88`、`isBuiltinRole` `:90-94`、`pointsFor` `:96-109`、`CustomRoleIDs` `:111-121`。
两道清理写在 `ReloadRoles` 里：与内置角色同名的行**直接忽略**（代码表才是内置档权威，
不许被库数据顶掉），字典里已不存在的点 ID **丢掉**（代码删了点，残留引用不该继续算数）。

为什么是进程内缓存而不是每次查库：判定入口（`RequireAdmin`、登录响应、`users` 校验）是
「只有角色字符串、没有仓储句柄」的纯函数，给它们统统加 `ctx` 与仓储会把功能轴的调用形状打散
（`catalog.go:8-11`）。角色定义属读多写少数据，**写侧每次成功写入后立刻 `ReloadRoles`**
（`internal/role/role.go:273`、`:351`、`:413`），所以同进程内可见性是即时的。代价记在 §11.2 第 11 条。

**装配**：`roleSvc := role.New(st.DB)` + `access.SetRoleStore(roleSvc)` + 启动时一次
`access.ReloadRoles`（`cmd/pipewright/main.go:125-132`，注入 HTTP 层在 `:652` 的 `httpapi.WithRoles(roleSvc)`）。
装载失败只记警告不 fatal：内置五档仍在代码表里，平台照样能鉴权，只是暂时看不到自定义角色。

**领域服务**（`internal/role/role.go`）只管自定义角色，判定不经过它——`Service` 同时充当
`access.RoleStore`（`:77` 有编译期 satisfies 断言）。三条硬边界都在写路径上挡：

| 规则 | 领域错误 | HTTP | 理由 |
|---|---|---|---|
| `settings.access` 不许分配给自定义角色 | `ErrSettingsPoint`（`normalizePerms` `:533-551`，判据 `:544-546`） | 422 `settings_perm_not_assignable`（`internal/httpapi/roles.go:277-279`） | 有了它就能建号、改角色、看审计、拿全局凭据明文，等于自制一个管理员 |
| 内置 id 不可改 / 不可删 | `ErrBuiltin`（`Update` `:292-294`、`Delete` `:390-393`） | 409 `builtin_role`（`:271-273`） | 模板要保持跨实例一致 |
| 仍被账号使用的角色不可删 | `ErrInUse`（`Delete` `:398-400`，包装里带人数） | 409 `role_in_use`（`:275-277`） | 留下指向不存在角色的 `users.role` 会变成「一个点都不给」的脏账号，不如让人先改派 |

另外：角色名去空后非空且 ≤40 字（`maxNameLen` `:49`，校验 `:233-239`）、名字大小写不敏感全局唯一
（`ErrDuplicateName` `:36-37`，409 `duplicate_name`）、点集里有字典外的 ID → `ErrUnknownPoint`
422 `unknown_perm`（挡前端过期名单与手拼请求）、`baseRole` 非内置名 → `ErrValidation`
400 `invalid_role`（`:240-243`，报错而不是静默清空）。唯一例外是**复制**：
`Copy`（`:363-386`）把源角色的 `settings.access` **静默剥掉**而非报错——从 admin 模板复制是常见起手式，
报错会让人以为复制坏了（`:360-362` 注释；UI 侧那个点渲染成「仅内置管理员」的禁用项）。

**端点**（`internal/httpapi/roles.go:1-14` 头部列全，注册在 `internal/httpapi/router.go:579-588`，
整棵 `/api/admin` 子树已挂 `RequireAdmin`，写方法吃 CSRF）：
`GET /api/admin/roles`（内置模板 + 自定义，带点集与 `userCount`）、`GET /roles/points`（点字典，
纯读代码所以无依赖；`settings.access` 标 `builtinOnly`）、`POST /roles`、`GET /roles/{id}`、
`PATCH /roles/{id}`、`DELETE /roles/{id}`、`POST /roles/{id}/copy`。
`svc == nil` 时六个端点统一 503 `roles_unavailable`（`:70-73` 等，便于不带库的演示模式）。
审计动作 `role_create` / `role_update` / `role_delete` / `role_copy`（`internal/audit/audit.go:126-129`）。
错误 → 状态码的映射集中在 `writeRoleError`（`internal/httpapi/roles.go:267-286`）。

**实效性**：`users.role` 从 `user` 改成某个自定义 id 仍是「换角色」，要**重新登录**才生效（§7）；
但改**已在使用中的角色定义**（勾掉一个点）不必重登——下次 `GET /api/auth/session`（含刷新页面）
就拿到新的能力位。已在手里的 HTTP 请求不会中途变档，所以最坏情况是那一瞬间多放行一次。

## 3. 用户 ↔ 角色 ↔ 分组 的关联链

这是本架构最容易讲错的环节，按数据流写实：

```
users (id UUIDv4, username UNIQUE, role, enabled)
  │  role 决定「功能轴」档位，取值是内置名(admin/user/…)或 roles.id(uuid v4)。
  │  admin 在 users 表有一行固定 UUID
  │  = users.BootstrapAdminRegularUserID = 00000000-0000-0000-0000-000000000001
  │    （internal/users/users.go:30-37，invariant 测试 internal/users/consts_test.go；
  │      改动会让所有已签发 admin personal 凭据的归属错位）
  │
  ├── sessions.user_id / sessions.role（迁移 `internal/store/migrations/sqlite/0053_session_user_binding.sql:31-32`）
  │     └── 登录时快照进会话：admin 登录 → 上面那个固定 UUID + role="admin"；
  │         普通用户登录 → 该用户 id + 该用户的 role（internal/auth/session.go:26-43）
  │         注意 role 是**会话里的快照**，不是每次请求 join users 表 —— 这直接导致
  │         §11.2 里「禁用账号 / 改角色都不立刻失效」的现状。
  │         快照的是**角色字符串**（可能是 uuid），点集每次判定现读缓存 —— 所以改角色
  │         定义不必重登，把账号改派到别的角色才要（§2.5 末条）。
  │
  ├── roles.id（自定义角色的归属：users.role → roles.id，无外键）
  │     └── 没有外键是有意的：删掉一个仍被引用的角色会留下脏行，所以写路径先用
  │         「仍有账号使用则拒删」挡门（role.go:398-400），而不是靠级联把角色抹掉。
  │
  ├── resource_groups.owner_id ── 组长（一个用户）
  │     └── 组长不写进名册表：resource_group_members 只存成员，
  │         「组长身份来自 resource_groups.owner_id，避免两处真相」
  │         （迁移 0055 头部注释:3）
  │
  ├── resource_group_members (group_id, user_id) 复合主键去重，
  │     group_id → resource_groups ON DELETE CASCADE（迁移 0055:8-15）
  │
  ├── credentials.owner_id ── personal 凭据的归属（迁移 0058_credential_owner.sql）
  │
  └── 资源侧：projects.group_id / servers.group_id / kube_clusters.group_id
        （迁移 0056:7 / 0057:6 / 0059:18；'' = 未归组）
        runs 表**没有** group_id：运行随项目走，
        归属解析由 Repository 内部做 run → project → group 两跳（access.go:48-49）
```

所以「用户属于分组」这件事在库里是**两条独立关系**：`resource_group_members.user_id`（名册成员）
和 `resource_groups.owner_id`（组长）。判定优先级上组长更宽（见 §5）。
角色与分组**互不推导**：`developer` 不会因为角色就看得见别人的组，组长也不会因为当组长
就自动获得设置类入口——两条轴各自独立判定，取更严的一档。
管理页把两条轴摆在同一个账号行里（角色下拉 + 「分组」弹窗多选，`web/src/views/admin/Users.vue:258-263`
写 `users.role`、`:310-322` 按差集逐条写 `/api/groups/{id}/members`），但**落的库、走的判定是两套**：
角色那一列写 `users.role`（或 `roles.id`），分组那几个勾选每改一条是一次名册写请求。

`users` 与 `admin_user` 的关系：`admin_user` 是单行表（id=1）承载首任管理员的口令，
`users.role='admin'` 的行是同一实体的 users 视角，两者由 `BootstrapAdminRow` /
`SyncAdminPasswordChange` 保持同步（`internal/users/users.go:1-16`）。
HTTP 层把这一行挡在写端点外（`isBootstrapAdminRow`，`internal/httpapi/users.go:125-131`），
所以管理员改自己的角色 / 停用自己是 409 而不是静默成功。

## 4. 一个请求依次经过什么

```
全局：chi Recoverer                          internal/httpapi/router.go:472
      localeMiddleware（本地化错误消息）      internal/httpapi/router.go:475

公开面（不鉴权，靠各自签名）：
  /api/webhooks/{token}   签名校验            internal/httpapi/router.go:495

```

第 3 步内部只有两次判定，且**功能轴先于数据轴**：

`accessGuardMiddleware`（`access_guard.go:75-104`）
→ `Service.Can`（`access.go:175-214`）
→ ① `Ceiling(actor.Role, kind)` 查表封顶（`access.go:182-189`，不碰库）
→ ② 读 `group_id` + 分组快照 → `Decide`（`access.go:197-212`）。

`accessGuardMiddleware` 的存在理由写在 `access_guard.go:15-23`：
`/api/projects/{id}/*` 与 `/api/runs/{id}/*` 合计三十多条路由，分散判定必然漏
（漏一条就是一个越权口子），所以按 URL 形态一次性收口，**新增路由自动被覆盖**。

它只认四种资源（`access_guard.go:42-70`）：`projects` / `runs` / `servers` / `kube-clusters`。
明确豁免的字面段：`projects/test-clone`（`:52-55`，没有既成资源可判）、`servers/metrics` 与
`servers/containers`（`:60-63`，聚合总览走「整表按可见范围过滤」，见 §8）。
`POST /api/projects`（创建）同样不归它管。

**档位映射只有一条规则**：`GET/HEAD/OPTIONS → ActView`，其余方法 → `ActOperate`
（`access_guard.go:91-96`）。注意它**不看角色**：角色上限在 `Can` 里面统一封，
所以这里不需要为每个角色加规则。

`svc == nil`（未装配权限仓储）时中间件直接透传（`access_guard.go:76-78`），
让单机演示与既有测试不受影响；生产装配恒定注入
`groupSvc := group.New(st.DB)` + `accessSvc := access.NewService(groupSvc)`
（`cmd/pipewright/main.go:121-122`）—— **同一个实例既当 `/api/groups` 的领域服务，
又当 `access.Repository`**，避免同一份名册两处缓存。

## 5. 数据轴的核心：`Decide` 的短路顺序

`internal/access/access.go:127-152`，按顺序命中即返回：

| # | 条件 | 结果 |
|---|---|---|
| 1 | `actor == nil \|\| actor.UserID == ""` | `ErrUnauthenticated` → 401 |
| 2 | `actor.IsAdmin()` | 放行 |
| 3 | `g != nil && g.OwnerID == actor.UserID` | 放行（**组长在组内拥有一切**，含改名册、把资源甩出组） |
| 4 | `act == ActManage` | 拒绝（未归组与公开分组没有「归属」可管，只有管理员能改） |
| 5 | `g.IsPublic()`（含 `g == nil` = 未归组） | 放行 |
| 6 | `g.HasMember(actor.UserID)` | 放行 |
| 7 | 其余 | `ErrForbidden` → 403 |

`Decide` 里**没有任何角色表查询**——它是纯数据轴函数，签名只吃 `actor / group / act`
（`access.go:127-130`）。功能轴封档发生在调用它的 `Can` 里（`access.go:182-189`），
所以 HTTP 之外直接调 `Decide` 的地方（`internal/httpapi/groups.go:148`、`:247`）
只判归属，不判角色档位——这是刻意分工，不是漏判：那些位置管的是「组归谁」，属 Manage 档。

三态语义（`access.go:6-9`、`internal/group/group.go:8-11`、迁移 0054 头部注释:4-6）：

| 归属 | 可见 / 可操作 | 谁能管归属（Manage） |
|---|---|---|
| **未归组** `group_id=''` | 全员可见可操作（存量数据全在这一态，不迁移） | 仅管理员 |
| **public 分组** | 同上 | 管理员 + 组长 |
| **private 分组** | 组长 + 名册成员 + 管理员；其余 403 | 管理员 + 组长 |

`Act` 三档（`access.go:52-58`，数值越大越重）：`ActView` 看得见（列表/详情/日志/报告）、
`ActOperate` 改得动（编辑/删除/触发运行/审批/部署/SSH 执行）、`ActManage` 管归属
（归组改组、私有分组成员名册）。

三处 **fail closed**，是这套设计里最重要的防守：

1. **悬挂引用**：资源的 `group_id` 指向已删的分组 → 按最私有一档处理
   （`access.go:205-209` 把快照替换成 `Visibility: private`），报 403 `group_missing`
   而不是「查不到组 = 放行」。`CanGroup` 那条路直接返回 `ErrGroupNotFound`
   （`access.go:85-86`、`:244-246`）。
2. **仓储未装配**：`Service.Can` 与 `VisibleGroups` 在 `s.repo == nil` 时只放 admin，
   普通用户一律拒（`access.go:190-196`、`:270-272`）。
3. **认不出的角色 / 类别**：`Ceiling` 退到 `ActView`（`roles.go:66-76`），`PermsFor` 给空集
   （`perms.go:190-209`）——前端据此把挂门入口全收起。库里有一条指向已删角色的脏 `users.role`
   时走的就是这一格（一个入口都不亮），而不是「按最像的内置角色凑一个档位」，
   理由写在 `catalog.go:15-16`：后者会把一条脏数据变成静默提权。

错误映射见 `access_guard.go:106-125`，**顺序敏感**：

| 判定 | HTTP | 错误码 |
|---|---|---|
| `ErrUnauthenticated` | 401 | `unauthorized` |
| `*ErrNotFound`（group / project / run / target） | 404 | `not_found` |
| `ErrGroupNotFound`（悬挂引用） | 403 | `group_missing` |
| `ErrRoleCeiling`（功能轴拦下） | 403 | `role_denied` |
| `ErrForbidden`（数据轴拦下） | 403 | `forbidden` |

404 判定刻意排在 403 之前（`access_guard.go:106-107`），否则「项目不存在」会被伪装成无权限。
`ErrRoleCeiling` 包装 `ErrForbidden`（`access.go:81-84`），所以既有的
`errors.Is(err, ErrForbidden)` 照旧生效，只有专门判它时才回一句真话：
「你的角色不允许这类操作，需要管理员调整角色」——提示去改角色，而不是让人去申请加入分组。

另外 `ErrForbidden` 选择明确回 403 而不是伪装 404，理由写在 `access.go:78-80`：
分组是协作资源，让人知道「资源存在但不属于我」比隐身更符合产品预期（用户据此去申请加入）。

## 6. 三条必须 handler 显式补判的例外

「读→View / 写→Operate」这条规则覆盖不到的，代码里都单独开了入口：

| 例外 | 为什么要补 | 位置 |
|---|---|---|
| **终端 / 远程文件：GET 也按 Operate** | WS 升级后无法回写 HTTP 状态码，必须在握手前挡下；「在目标机上跑任意命令」语义上是操作。`/fs*` 全是读写混合，列表 GET 也算操作 | `access_guard.go:127-145 requireTerminalOperate`；调用于 `container_terminal.go:122`（容器 WS）、`:222`（主机 shell WS）、`fs_upload.go:376-383 requireFSAccess`（被上传/文件各端点共用，`fs_upload.go:413/547/718/773/873` + `server_fs.go:105`） |
| **ActManage：归属级动作** | 中间件规则里没有 Manage 档；且归组要判**新旧两侧** | `access_guard.go:160-176 requireResourceManage` → `servers.go:230`（改归属，旧侧）、`:281`（删主机）、`kube_clusters.go:197`、`:246`；`access.go:227 CanGroup` 判新侧 → `projects.go:131-155 requireGroupPlacement`（用于创建 `:177`、PATCH `:247`）、`servers.go:126-134 requireServerPlacement`（也用于集群登记，`kube_clusters.go:141`） |
| **admin 档：与分组无关的全局设置** | 分组判定管不到「设置类」动作 | `RequireAdmin`：`GET /api/audit`（`router.go:525`）、`POST /api/credentials/{id}/reveal`（`:536`）、`/api/admin/*` 整棵子树（`:541-593`：build-envs、config-profiles、users CRUD、**roles CRUD**、凭据启停）、`POST /api/groups` + `DELETE /api/groups/{id}`（`:614-615`） |

第 3 条已收口（提交 `fc13b37`）：`RequireAdmin` 现在判的是 `access.SettingsAllowed(sess.Role)`
（`internal/httpapi/middleware.go:111`），也就是 `settings.access` 这个功能点，不再读
`Session.IsAdmin()`。今天取值仍与「`admin` 或旧会话 `''`」完全等价（这个点只授予内置管理员，
`perms.go:97`；自定义角色在写路径上就被挡住，`role.go:544-546`），但左栏入口、路由落点、
这层服务端门从此出自同一张表，不会再出现「给某角色开了设置点、页面进得去而端点全 403」
（原 §11.2 第 8 条已消）。

两条产品决定值得单独记：

- **登记一台未归组主机 = 向全员开放一个可 SSH 的目标**，所以新建未归组服务器收在管理员
  （`servers.go:126-141` 注释与 `requireServerPlacement`）；组长只能在**自己的组里**加机器。
  改归属（PUT）则两侧都要管得住：旧侧 `requireResourceManage` + 新侧 `requireGroupPlacement`
  （`servers.go:230-234`）。
- **更换组长只有管理员能做，组长本人说了不算**（`internal/httpapi/groups.go:291-293`）——
  换组长是权限边界改动，不能让既有边界内的人自授。
  分组的建/删是 admin-only（`router.go:614-615`），改名 / 描述 / 可见性 / 名册是 admin 或组长
  （`groups.go:276`、`:347` 走 `loadGroupForActor(..., access.ActManage)`，实现在 `:237-252`）。

## 7. 身份轴细节

- **会话**：`sessions(token, csrf_token, user_id, role, created_at, expires_at, last_seen_at)`。
  token 与 CSRF 各 32 随机字节（64 hex，`internal/auth/session.go:19-20`）。TTL 7 天 +
  **滑动续期**，但只在距上次 `last_seen` 超过 60s 才写库，避免每请求一次 UPDATE 的写放大
  （`session.go:13-21`）。
- **旧会话兼容**：`role=''` 在 `RequireAdmin` 里**按 admin 放行**
  （`internal/auth/rbac.go:42-49`、`Session.IsAdmin` `internal/auth/session.go:46-53`），
  注释写明理由是「避免升级锁死旧部署的管理员」。这类会话要登出重登一次才带上明确 Role。
  反过来 `RequireUser` **拒绝**空串（`internal/auth/rbac.go:51-58`）：普通用户端点要求明确角色。
- **登录**：先查 `admin_user` 单行、再查 `users` 表两条路径（`internal/auth/service.go:156-183`）。
  两个反枚举设计：用户名用 `subtle.ConstantTimeCompare` 恒定时间比较（`service.go:175`）；
  用户不存在时仍跑一次 argon2id（`dummyHash`，`service.go:48-56`）。`dummyHash` **必须是静态常量**——
  在 `init()` 里现算会让进程空载常驻内存永久抬高 ~64MB（实测 18MB→82MB），逼近 NFR-4 的 ≤100MB 红线。
- **锁定**：连续失败 5 次 → 锁 15 分钟（`internal/auth/lockout.go:8-12`）。
  当前是**内存计数器**（进程重启清零）、单管理员实例的全局单一计数、不按 IP/用户分桶
  （`lockout.go:24-28` 自注为后续可选扩展）。
- **口令规则**：新口令至少 8 位（`service.go:35-36`）；改口令要校验当前口令
  （`ErrInvalidCurrentPassword`，`service.go:29-30`）。**首登强制改密未实现**（独立 story）。
- **普通用户端点**：`RequireUser` 接受任一已知角色（内置名或已装载的自定义 id，判据见上），未登录 401。
  挂在 `/api/build-envs`、`/api/build-envs/languages`、`/api/config-profiles`（只读已启用项）
  与 `/api/groups*` 的读写侧（`router.go:596-616`；建组 / 删组另挂 `RequireAdmin`）。
- **能力位下发**：`POST /api/auth/login` 与 `GET /api/auth/session` 的响应体除 `username` /
  `role` 外还带 `capabilities`（`router.go:1179-1192`，`sessionPayload` `:1184-1188`；
  两处调用 `:1166`、`:1239`）。它是 `access.CapabilitiesFor(role)` 的查表结果
  （`roles.go:116-124`，结构体 `Capabilities` `:98-109`：`settings` + `kinds` + **`perms`**，
  后者即 §2.3/§2.5 合并后的角色点集：内置档来自代码表，自定义档来自 `role_perms`），
  **只供前端决定入口显不出现**，服务端每个请求重新判、不以它为准。
  `role` 需先过 `sessionRoleOf`（`internal/httpapi/router.go:1170-1177`，旧会话空串按 `admin` 报出去）。
  正因为 `perms` 是**每次拉会话现算**的，改了角色定义不必让对方重登，刷新页面即可（§2.5 末条）。
- **改角色**：`PATCH /api/admin/users/{id}` 带 `role` 时走 `users.SetRole`
  （`internal/httpapi/users.go:294-300` → `internal/users/users.go:301-310`），库改了但**会话里的 role 不变**，
  对方要重新登录才换档（见 §11.2 第 1 条）。校验用 `ValidRole`，所以传自定义角色的 uuid 是合法的。

## 8. 列表的可见范围：不逐条判定，改成集合作为条件

逐条 `Can` 在列表场景是 N 次查库，所以列表走另一条路：

- `access.go:262-279 VisibleGroups(actor)` → admin 直接 `ListFilter{Unrestricted: true}`（不查库）；
  普通用户拿「所有 public 组 + 自己作为组长或成员的 private 组」，并且

  会凭空从列表里消失。**注意它不看角色上限**：`viewer` 与 `user` 的可见集合相同，
  差别只在能不能动手（见 §12「两条轴各自只有一个收口」）。
- `access.go:281-301 ListFilter.Clause(column)` 编译成 `column IN (?,?)`；
  `Unrestricted` 返回空串让调用方跳过条件；`GroupIDs` 为空也**仍生成条件**
  （`column = ''`，`:287-290`），注释明说「不能退化成无条件放行」。
- 六个入口在用（都走 `visibleGroups(r, svc)`，`access_guard.go:147-158`）：
  `projects.go:106`、`runs.go:203`、`servers.go:92`、
  `server_metrics.go:953`（`GET /api/servers/metrics` 聚合）、
  `server_containers.go:240`（容器总览聚合）、`kube_clusters.go:87`。

## 9. 凭据分级轴

- `internal/vault/rbac.go:41-60 effectiveFilter(actor, requested)`（函数体 `:50` 起）：
  admin / nil → 请求什么给什么；普通用户 → **强制把 `OwnerID` 覆写成自己**
  （忽略调用方传的别人的 id），视角 = 共享凭据 ∪ 自己的 personal。
- `vault.go:606-656 ListWithActor`：共享的 `scope <> 'personal'` 与自己的 personal
  **必须写在同一条 SQL 里**，否则「both + owner」会被误当成不过滤 owner 而泄漏他人 personal。
  用 `scope <> 'personal'` 而非 `= 'global'`：0058 之前建的老凭据 `scope` 是空串，
  等值判定会让它们在列表里凭空消失（`vault.go:617-619`）。
- **为什么 global 凭据不对普通用户隐藏**（`internal/vault/rbac.go:46-49` 整段注释）：存量部署的凭据
  **全是** global，项目/服务器配置都引用它们，藏起来会让非管理员的项目页显示成「未选择凭据」
  并无法再选回来——那不是收紧权限，是把老数据打死。列表只出掩码，引用不到明文；
  写 / 删 / 读明文仍有独立的门。
- 读明文：`GetWithActor`（`vault.go:664`）/ `RevealWithActor`（`:677`）都先 `authorizeRead`
  （`:763-779`；personal 且 owner 就是本人 → 放行，global 且非 admin → `ErrForbidden` `:775-777`，
  其余（别人的 personal）→ `ErrAccessDenied` `:778`）。
  HTTP 层再收一层：`POST /api/credentials/{id}/reveal` 挂 `RequireAdmin`（`router.go:536`），
  即**本期连所有者本人都不能 reveal 自己的明文**，只能删了重建。
- 启停：`DisableWithActor` / `EnableWithActor`（`vault.go:707-716`）要求 admin 且凭据
  `scope='personal'`，禁用只改 `enabled` 元数据、密文留着，但取用路径立刻报
  `ErrDisabledCredential`（`internal/vault/rbac.go:70-71`；触发点 `vault.go:303/349/390`）——
  这正是「立刻停用一把可疑令牌」的效果。
- 创建 `scope='personal'` 却不给 `owner_id` → `ErrOwnerRequired`（`internal/vault/rbac.go:66-68`、`vault.go:220`）：
  没有归属的个人凭据等于没人能看见，入参阶段直接拒，而不是静默落成 global。
- **这条轴完全不看功能点表**：vault 的 `Actor` 只有 `UserID / Role` 两个字段
  （`internal/vault/rbac.go:13-20`），`developer` / `ops` / `viewer` 在 vault 眼里都等同 `user`。
  也就是说角色档位目前不约束「能不能读某把密钥」，约束它的仍是 admin / owner / scope。

## 11. 已知缺口与风险（本期只记录，不改行为）

按「影响面 / 是否有意为之」分两类。

### 11.1 唯一的非对称收口（看起来是漏收，非取舍）

**删除项目只判到 Operate，没有像删主机 / 删集群那样补 Manage。**
`makeDeleteProjectHandler`（`internal/httpapi/projects.go:285-287` 起）直接 `svc.Delete`，
归属判定全靠 `/api` 组中间件，而中间件规则是「GET → View，其余 → Operate」。后果：
**私有分组的普通成员也能删掉组内任意项目**（角色得是 `admin`/`user`/`developer` 才有 Operate）。
对照删主机（`servers.go:281`）与删集群（`kube_clusters.go:246`）都显式补了 `ActManage`，
理由是「删除是归属级动作」。

真机矩阵 C 段没有「成员删项目被 403」这条断言——因为实现就是放行，断言会与实现互相印证而失效。
收紧方式：`makeDeleteProjectHandler` 补一行 `requireResourceManage(w, r, acc, access.KindProject, id)`
+ 一条 403 断言。**决定：本期不动**（会改变私有组成员的既有能力，属产品决定）。

### 11.2 有意的取舍（源码注释里都写了理由）

1. **禁用账号、重置口令、改角色都不撤销已签发会话**：`role` / `enabled` 是登录时快照进
   `sessions` 的（`internal/store/migrations/sqlite/0053_session_user_binding.sql:31-32`），
   禁用后旧浏览器仍能继续操作，只挡新登录；改完角色也要**重新登录**才生效
   （`internal/users/users.go:296-300` 明写，用户在管理页上看到的提示文案与之同源）。
   要「禁用 / 改角色 = 立刻失效」需要一张会话撤销表。
   **角色可配置之后这条只说对一半**：快照的是角色**字符串**，点集每次判定现读缓存
   （`catalog.go:96-109`），所以改**角色定义**不必重登，对方刷新页面就会拿到新能力位；
   把账号**改派**到另一个角色才需要重登。用户已接受这个口径（本期明确「实效性不用管」）。
2. **旧会话 `role=''` 按 admin 放行**：为不锁死升级前的管理员
   （`internal/auth/rbac.go:42-49`、`roles.go:70-72`、`perms.go:177-182`）。
3. **未归组资源对全员开放写**（含改内容），只有归属收在管理员手里——
   存量数据不迁移，升级当天不能把别人的项目变成「谁都看不了」。代价：想保护一个项目必须显式建组并归组。
   档位在这条路上仍然生效：`viewer` 改 / 删一个未归组项目实测 403（走中间件的 Operate 判定）。
   **但「新建」这条路完全不吃档位**，见 §11.4 第二条。
4. **reveal 明文只开放给管理员**，所有者本人也不能读自己的明文（`router.go:536`）。
5. **登录失败计数是内存的、单管理员全局一份**：重启清零、不分 IP（`lockout.go:24-28`）。
6. **首登强制改密未实现**。
7. **`ops` 不能发起构建**：手动触发流水线按 URL 属 project 档，`ops` 的 project 上限是
   `view`（`roles.go:28-30`；点集里没有 `project.trigger` 这种粒度）。放开它要么把 `Kind`
   拆细（触发运行 vs 改项目配置），要么给「触发」单开一个功能点，本期刻意留在注释里没做。
   现在管理员可以在页面上建一个带 `project.edit` 的自定义角色绕过这条，但那是**给它项目上限**，
   不是给它「触发」这一格——粒度问题没变。
8. **设置类入口已收到功能点上**（`fc13b37`，见 §6 第 3 条）：`RequireAdmin` 判的就是
   `settings.access` 点（`internal/httpapi/middleware.go:111`）。今天取值仍等于「内置 `admin` 或
   旧会话 `''`」，但今后给某角色开设置页只改 `perms.go` 一行，前端三处门
   （`web/src/views/Permissions.vue:22` 与 `web/src/router/index.ts:182`、`:190`）与这层中间件同时跟上。
   **自定义角色拿不到这个点**（写路径 422 挡死，§2.5），所以「进得了设置」至今仍是内置管理员专属。
9. **`ActManage` 不受角色上限约束**（`roles.go:11-13`、`perms.go:20-22`、`access.go:184`）：所以一个角色是
   `viewer`（写请求全 403）但**同时是某组组长**的用户，仍能在自己组里改归属、改名册、删主机
   ——因为组长在第 3 步就放行了，根本没走到档位。反过来想管**别人的**公开分组也管不动：
   挡住它的是 `Decide` 第 4 步（未归组与 public 组的 Manage 只有管理员能过，`access.go:141-143`），
   而不是角色表。设计如此，但读代码时容易以为角色表能兜住这类情况。
10. **能力位与真机矩阵的覆盖分工**：功能轴（点集与派生档位）只有 Go 单测
    （`internal/access/roles_test.go`、`perms_test.go`、`roles_drift_test.go`、`catalog_test.go`、
    `internal/role/role_test.go`、`internal/httpapi/role_guard_test.go`），`scripts/perm-matrix.py`
    里没有角色断言（grep `role_denied` 为 0 命中）；真机矩阵覆盖的是归属轴。
    入口显隐这一层目前有真机人工核对（见 §11.4 第一行的验证记录），但没有写进 `perm-matrix.py`。
11. **自定义角色是「进程内」可见**：`ReloadRoles` 只刷本进程缓存（`catalog.go:57-88`），
    写路径写完立即刷（`role.go:273`、`:351`、`:413`），所以**单进程部署没有观测差**。
    多实例部署时另一台要到下次重载（重启 / 下一次本地写入触发的全量刷）才看见新角色定义，
    其间那台机器上的 `users.role = <新 uuid>` 会认不出来 → 一个点都不给（fail closed，不会提权）。
    真要多实例得改成 TTL 刷新或跨进程通知，代码注释里已把这条列成后续（`catalog.go:12-13`）。
12. **账号没有删除端点，所以删角色要先改派**：`DELETE /api/admin/users/{id}` 不存在
    （路由只有 GET/POST/PATCH 与口令重置，`router.go:573-577`），实测 405。后果是「想删一个自定义角色」
    必须先把挂在它上面的账号改派到别处（`role_in_use` 409 会带回人数），
    而不是像分组那样删掉容器即可。清理一个测试账号的可行路径只有 `PATCH {role, enabled:false}`
    这一条——禁用会让它挡在新登录之外，但已签发的会话照旧能用（第 1 条）。
13. **角色展示名不走 i18n**：`roles.name` 是管理员起的业务称呼（迁移 `0062_roles.sql:9` 注释），
    切语言不会翻译它；内置五档另有 `ROLE_LABEL_KEY` 的八份键。所以同一张下拉里可能混着
    「开发者（模板译文）」和「发布值班（用户起的中文名）」两种来源的标签，
    由 `labelForRoleId`（`web/src/lib/roleEditor.ts:170`）统一取。

### 11.4 本期没做的两档粒度（记录，不改行为）

1. **功能点只管到「入口 + 路由」，没管到页面内的按钮**。`sessionStore.can` / `canPerm`
   在页面里**一处都没被调用过**（`grep -rn "\.can(" web/src` 只命中
   `web/src/stores/session.test.ts` 与 `session.ts` 自身），所以 `ops` 打开项目流水线页仍看得到
   「保存草稿」，`viewer` 也看得到「新建项目」。点了会 403（后端 `min(角色上限, 分组授予)` 是权威），
   但「按钮亮着、点了被拒」是产品体验问题，不是越权。真机核对（本机 :8080，四个角色
   各登一次，2026-09-29）：developer / ops / viewer / user 的左栏都是 13 条业务入口 +
   用户与权限 + 设置；只有 admin 多出「通知 / 构建环境 / 配置资源」三条；
   `/servers/{id}/terminal`、`/library/studio`、`/settings/notifications`、`/build-envs`、
   `/config-profiles` 按点各归各位（developer 进不了终端，ops 进不了工作室，
   非管理员进不了任何设置子页），`/settings` 对无设置点者落 `account`、对管理员落 `ai`。
   下一档要做的是给写操作按钮挂点（保存 / 触发 / 回收 / 删容器各是一个点），
   并给 `perm-matrix.py` 补角色断言。
2. **「新建资源」这条路完全不吃功能轴**。`requireGroupPlacement`
   （`internal/httpapi/projects.go:135-155`）对 `groupID == Ungrouped` 直接 `return true`
   （`:136-138`），而创建路由 `POST /api/projects` 不带 `{id}`，不会被
   `accessGuardMiddleware`（`access_guard.go:75-104`）覆盖。后果（实测）：角色是 `viewer`
   或 `ops` 的用户 `POST /api/projects {"groupId":""}` **返回 201**——建出来的项目未归组，
   于是全员可改（§11.2 第 3 条），只读角色顺手开了一个谁都能写的口子。
   两种收法：创建也判一次 `Can(..., ActOperate)`（未归组时用合成的 public 快照，需要
   `Can` 允许 `id == ""` 这条特殊路径），或给创建单开功能点（`project.create` /
   `server.create`）并在 handler 里判。**决定：本期不动**——这会让今天能建项目的
   普通用户里「只读角色」那一档突然建不了，属产品决定；且 `viewer` 本来也不该建，
   先记录等定口径。

## 12. 加判定 / 加用例的正确姿势

- **两条轴各自只有一个收口**：功能轴的权威是**三处**——点字典 `permDict`
  （`internal/access/perms.go:48-82`）、内置模板点集 `rolePerms`（`:95-122`）、
  库里的自定义角色（`roles` / `role_perms`，经 `internal/access/catalog.go` 进程内缓存），
  判定侧唯一的取数入口是 `pointsFor`（`catalog.go:96-109`：**先代码表、再缓存**）；
  档位是从点集**派生**出来的（`Ceiling`，`internal/access/roles.go:66-92`），
  所以不存在第二张需要同步的档位表。数据轴改 `Decide`（`internal/access/access.go:130-152`）。
  生效顺序（先封档后查库）写在 `Service.Can`（`access.go:175-214`），**不要**在 handler 里加
  「这个角色能不能…」的判断，也不要把 `NormalizeRole`（`roles.go:45-59`，自注 `:48-50`）接进判定——
  它认不出脏值时会退成 `user`，那是「读起来顺」而不是「权限够」。
- **加一个角色 = 在页面上建，零代码**（「用户与权限 → 角色」，§2.5）。走 `POST /api/admin/roles`
  （路由 `internal/httpapi/router.go:579-588` → `internal/role/role.go:232`），
  写完当场 `ReloadRoles`（`role.go:273`），于是 `ValidRole`（`perms.go:169-175`）、
  `RequireUser` 的判据 `IsUserSession`（`internal/auth/rbac.go:56-58`）、`SetRole`
  （`internal/users/users.go:301-305`）、`Ceiling` / `SettingsAllowed` / `CapabilitiesFor`
  （`roles.go:66/96/117`）全按同一张 `pointsFor` 认它，前端下拉与标签由服务端下发、
  经 `labelForRoleId`（`web/src/lib/roleEditor.ts:170`）取名。**不需要发版、不需要加 i18n 键**。
- **只有想把一档做成「内置模板」（跟着后续新点自动演进、且不许管理员改删）才动代码**，
  改这几处：`internal/access/roles.go` 常量（`:23-34`）+ `Roles()`（`:36-39`）+
  `internal/access/perms.go` 的 `rolePerms` 一行名单（`:95-122`）；前端 `web/src/api/auth.ts`
  的 `UserRole` 联合类型（`:19`）、`web/src/lib/roles.ts` 的 `ROLE_ORDER`（`:19`）/
  `ROLE_LABEL_KEY`（`:22-28`）/ `ROLE_TAG_CLASS`（`:31-37`）+ 8 语种文案。
  漏一处就会响：`roles_drift_test.go:63`（前端名单 == `rolePerms` 键集且每档有展示键）与
  `:95`（`Roles()` == `rolePerms` 键集）。内置档改名 / 删档属口径变更，另见下条冻结矩阵。
- 新增一个功能点：在 `permDict` 追加一行（`{ID, Kind, Act}` 三字段在 `:31/:33/:35`；ID 里不出现
  路由路径，改文案不改 ID），`Kind` 必须是 `ResourceKinds()`（`roles.go:111-114`）里的四类之一或
  `Platform`——写成别的字符串不会报错，只会让那个点永远派生不出档位（`TestPermDictSane`，
  `perms_test.go:15` 拦这一手）；`Act` 只允许 view / operate（`perms.go:20-22`）。
  **两类角色的跟随方式不同，这是 P4 之后最容易踩的一条**：
  - 内置模板按代码走，`admin`（`permIDs()`）与 `user`（`permsWithout(settings.access)`）自动拿到新点，
    `viewer` 由 `permsWhere` 筛（新点是 `*.view` 就自动给），只有 `developer` / `ops` 是手抄名单，
    不给就不给；
  - **自定义角色不会自动拿到新点**：库里存的是名单快照，新点对它们默认关闭，
    要管理员在角色编辑页勾一次。反过来删掉一个点时残留引用会自动失效
    （重载时按字典过滤，`catalog.go:58-59`、`role_test.go:220` 钉住）。
  前端要让入口跟着亮才加进 `PermId` 联合类型（`web/src/api/auth.ts:33-54`）并在 `navItems` /
  `meta.requires` 引用它；`roles_drift_test.go:120` 会比对联合类型与三处引用是否等于字典。
- **守卫全在 Go 侧**（前端 tsconfig 没有 node 类型，测试读不到文件，所以漂移只能这么钉）：
  上述三条 `roles_drift_test.go`（`:63`、`:95`、`:120`），加 `perms_test.go:53` 把内置档派生出的
  档位**冻结**在今天这版矩阵上——改点集时它第一个响，真改了档位要连同那张期望表一起改，
  那是显式的口径变更，不该顺手带过；自定义角色的写侧规则由 `internal/role/role_test.go`
  （`:55` 建/查/列、`:103` 各类拒绝、`:129` 改点集与挡内置、`:160` Copy 剥设置点、
  `:182` 删档三道守卫、`:220` 字典外点丢弃、`:244` 在用量回显）与
  `internal/access/catalog_test.go`（`:36`、`:73` 不许顶掉内置、`:91` 未知角色 fail closed、
  `:114` 重载失败保留上一次快照、`:135`、`:150`）覆盖；HTTP 侧的档位与能力位断言在
  `internal/httpapi/role_guard_test.go`（`:63`、`:102`、`:169`）。
  **改前端文件里的角色名单 / 点引用后要用 `go test -count=1`**：Go 的测试缓存不因
  `os.ReadFile` 读到的内容变化而失效，加不加自定义角色相关的守卫都可能在缓存里假装通过。
- 新增 `/api/{projects|runs|servers|kube-clusters}/{id}/*` 路由**自动被中间件覆盖**，
  不要在各 handler 里重复判 View/Operate；只有 Manage 档、以及「GET 但语义是操作」的通道
  才需要显式补判（§6）。
- 加真机用例：先在 `internal/access` 的表驱动单测补全判定矩阵（归属轴 `access_test.go`、
  功能轴 `roles_test.go`），再在 `scripts/perm-matrix.py` 加一条真机断言，然后
  `python3 scripts/perm-report.py` 重生成报告（流程与夹具见 `docs/分组权限测试报告.md` §8）。
  功能轴要加真机断言的话，注意 `perm-matrix.py` 目前一条角色用例都没有，
  而且它按内置档建的测试账号也不会自动拿到新点（§11.2 第 10 条）。
- 未覆盖项及它们各自的替代验证位置，列在 `docs/分组权限测试报告.md` §6
  （WS 终端握手、悬挂引用、MySQL 方言、并发竞态）。
