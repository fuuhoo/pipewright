### 2.10 分组权限(P0–P5,本轮新增)

需求:项目/服务器可归属分组,分组分公开/私有;私有组只有组长 + 名册成员 + 管理员能看能操作,运行信息随项目走。

| 层 | 落地 | 关键取舍 |
|---|---|---|
| 数据 | `0054` resource_groups、`0055` resource_group_members、`0056` projects.group_id、`0057` servers.group_id、`0058` credentials.owner_id | 表名带 `resource_` 前缀(MySQL 8 保留 `groups`);`group_id` **不建外键**——ON DELETE SET NULL 与 NOT NULL 冲突,且静默删组会留下悬挂引用 |
| 判定 | `internal/access`:`Decide` 纯函数 + `Service.Can/CanGroup/ForRun/VisibleGroups` + `ListFilter.Clause` | 三态:`group_id=''`(未归组)= 全员可见可操作(存量数据即此态);public 同上;private = 组长/成员/管理员 |
| 分组领域 | `internal/group`:CRUD + 名册,并实现 `access.Repository` | 删组要求先移空(`ErrGroupNotEmpty`);悬挂引用按最私有一档收敛(fail closed) |
| HTTP 收口 | `internal/httpapi/access_guard.go`:挂在 `/api` 上的**一条**按 URL 形态识别的中间件 | 逐个 handler 判定必漏;读→View、写→Operate;更高档 Manage 由 handler 显式判(归组要管住新旧两侧) |
| 项目/运行 | 列表按可见分组收敛;`PATCH` 带 `groupId` 时判两侧 Manage;运行经 run→project→group 两跳 | 拒绝语义 = **403 明确无权限**(不伪装 404);资源不存在仍 404 |
| 主机/容器 | 列表 + 两个批量总览(`servers/metrics`、`servers/containers`)走 `ListScoped`;`POST/PUT/DELETE /servers` 归属闸门;WS 终端(主机 + 容器)握手前按 **Operate** 把关 | 登记一台**未归组**机器 = 向全员开放一台可 SSH 目标 → 仅管理员;移组到未归组则组长也允许(已判过原组 Manage) |
| 审计 | `group_*`、`project_reassign`、`server_create/update/delete/reassign` | 归组单独成条:事后追问「谁把这项藏起来的」时是第一条要看的记录 |
| 前端 | `/groups` 分组管理页(建组/改名/可见性/名册增删)、项目列表与新建弹窗带归属选择、主机登记/编辑同样、用户管理页补建号 + 重置口令 + 启停 | 会话 DTO 只有 `{username, role}`,所以 `canManage` 由 Go 侧 `access.Decide` 盖好再下发,UI 只读不算;选择器规则与 `requireServerPlacement` 逐条对齐(未归组主机只有管理员能新建,组长必须落到自己组) |
| 403 态 | 项目流水线页 / 运行详情页把 403 渲染成「无权访问:该资源属于私有分组,你不在名册里」+ 重试 | 不伪装 404:与后端拒绝语义一致,用户知道去找组长而不是以为数据丢了 |
| 项目页分组筛选 | 工具栏「全部分组 / 未归组 / 各可见分组」下拉,与搜索、状态筛选叠加;空态的「清除筛选」一并复位 | 候选直接取 `GET /api/groups`(后端已按名册收敛),前端不重推可见性规则 —— 局外人的下拉里天生没有别人的私有组 |

真机测试(P5):管理员 / 组长 / 成员 / 局外人四路身份,**79 条断言全绿**,逐条结果见 `docs/分组权限测试报告.md`(夹具与脚本 `scripts/perm-matrix.py` 保留可重跑)。结论:私有组内的项目、运行、主机在局外人的列表里消失且直连 403;成员能看不能管名册;组长能管名册与组内资源,也能把组内项目挪回未归组;未归组资源仍全员可用但归属只由管理员动;禁用账号无法登录。

已知取舍:**禁用与重置口令都不撤销既有会话**(与管理员改自己口令同一套语义,`users.go` 注释已记)。改密的直觉是「立刻失效」,若要真做到需要会话撤销表,留待后续。

### 2.8 v6.2 收尾追加:镜像来源消灭到手填不可达(R4 全链路)

设计文档没写这么细,但这是「所有构建环境都来自预设」这句话的真正边界,逐条记录:

| 通路 | 原状 | 现状 |
|---|---|---|
| 节点表单 `image` 输入 | script/build_frontend/build_backend/templated/build_image 可手填 | 控件删除,改「构建环境」目录选择器;`image`/`toolchainLanguage`/`toolchainVersion` 由该控件托管(`managedKeys`),值仍在 config 里(后端按旧键查目录) |
| 「高级 · 原始参数」 | 可绕过表单手加 `image`/`registry` 键 | 受管键 + 已删假字段在失焦时撤销整行(`JobDrawer.onExtraBlur`) |
| 默认配置 | `defaultConfig` 写死 `node:20-alpine`/`maven:3.9-...` | 全部删除;单测断言「任何 spec 的 defaultConfig 不得含 image」 |
| push_image 的 registry/imageName/tag/credentialId | 四个输入框无执行侧消费者(假字段) | 删除,改「推送目标」只读回显;registry 与登录凭据来自**运行所在环境**绑定的镜像仓 |
| 保存期 | 不校验 | `enforceBuildEnvCatalog` → 422 `build_env_required`(错误消息含阶段/节点/镜像,无 secret) |
| 执行期 | `toolchainImage()` 自己拼 `语言:版本` | `buildenv_runtime.go` 只认目录:`EnvID` → `image`(必须在目录内) → 语言+版本;目录没有 → 拒绝执行,**不迁移旧配置** |
| AI 生成 | 提示词让模型自填镜像 | 提示词注入「可用构建环境」清单(仅 enabled),只准写 `buildEnvId`;apply 遇目录错误 → 422 而非 500 |
| 只带 `buildEnvId` 的 build_image(工具链) | 语言/版本空 → 解析失败 | 执行期按目录条目回填 `Toolchain{Language,Version}`(`runBuildImageJob`) |

**明确豁免(按你定的边界保留手填)**:阶段旁挂服务 `StageServicesEditor`、阶段后置步骤、非 DAG 的 `settings.Steps[].Image` 三处仍手填镜像 —— 它们不是「构建环境」而是临时 side-car/清理容器。

### 2.9 任务类型收敛(v6.2 之后追加,不在原设计文档内)

起因:picker 里 11 个类型语义交叉(「构建」与「前端构建/后端构建」并列、`health_check` 是假绿门禁、`custom` 是 `script` 的别名)。按云效的「阶段 → 任务 → 步骤」模型收敛为动词级类型,**旧类型一律不迁移数据,报错要求改配**。

| 项 | 原状 | 现状 |
|---|---|---|
| `health_check` 节点 | 永远绿色放行,不探任何东西 | **类型撤销**(`pipeline.retiredJobTypes`):保存 422 `invalid_job`、本地/远程执行三条派发路径各自失败并给改配指引 |
| 健康门控能力 | 无 | 并入部署任务:表单「健康探测」(none/http/command) → config `healthProbe/healthUrl/healthCommand/healthRetries/healthInterval/healthTimeout` → `deploy.HealthCheckFromConfig` → 复用 `internal/deploy/healthcheck.go` 在**同一条 SSH exec 链路**逐机探测;不通 → 该机 failed,产物部署与 `command` 型部署都门控 |
| 半截探测配置 | (新风险)选 http 不填 URL 会静默退化成「不探测」 | 保存期 422 + 执行期 `ErrBuildFailed` 双卡;`expectStatus` 假字段不迁移(执行侧是 `curl -fsS`,无期望码概念) |
| `deploy_frontend` / `deploy_ssh` | 两个类型两套字段,实际同一条执行路径 | **picker 只剩「部署」**(`deploy_ssh`);前端静态站点改成部署任务卡下的**模板胶囊**(点它 = 插任务 + 预填 dist/rolling/nginx reload)。`deploy_frontend` spec 保留(存量节点照常渲染/执行),节点名标「旧版前端模板」;改配方式是抽屉里「更换任务类型 → 部署」,配置键全保留,不需要迁移。AI 节点目录同步删掉 deploy_frontend |
| `custom` = `script` 的别名 | 前端两份 spec 复制粘贴,用户看到两个一样的类型 | spec 改标 `aliasOf: 'script'`(与 script **共用同一份字段定义**),picker 里从不出现;编辑器保存时 `canonicalJobType` 把存量 `custom` 收敛成 `script`(config 原样)。后端 `scriptJobTypes` 仍含 `custom`,旧流水线/`.pipewright.yml` 不动也照跑 |
| `build` / `build_image` / `build_frontend` / `build_backend` | 三张构建卡语义重叠:前端/后端构建 = 预填命令的脚本节点,「构建」= 另一种产物路径,用户得先理解差别才知道选哪个 | **合并为一个 `build` 任务**:`config.artifactType`(image / jar / dist)是第一件事,档位决定表单与执行路径 —— `pipeline.EffectiveJobType` 把 image 档折到 `build_image` 路径(dockerfile 或 toolchain),jar/dist 档折到 script 路径(容器跑 commands + 收 artifactPath)。三条派发路径(非 DAG 分组、job 级 DAG、远程 runner)与 `NeedsBuildEnv` 都只认折算结果。档位缺失保存 422 `invalid_job`(不猜路径);旧三型的 spec 保留,存量节点照常渲染执行,picker 里不再出现。前端/后端构建同时降级为 `build` 卡下的**模板胶囊**(前端 dist / 后端 jar / Docker 镜像三条配方) |
| `push_image` 节点 | 与 `build_image` 并排的独立节点,但真实推送一直发生在构建路径里(它只影响一行提示日志) | 推送改由构建任务的**「构建后推送」开关**(`config.pushImage`,缺省 = 推送即旧行为)决定:关掉就只构建、镜像留本机并打一行说明。`push_image` 降级为纯编排/展示节点(存量流水线靠它排 DAG 顺序的仍可用),picker 移除。AI 节点目录同步:构建/推送/部署/脚本/通知只剩一条 `build` 条目 + 档位说明 |
| 产物档位 `image / jar / dist` | 上一行留的三档:jar 与 dist 在执行路径上本来就同一条(容器跑 commands + 收 `artifactPath`),用户却要先判断「我的产物算 jar 还是 dist」 | **收敛为两档**:`image`(容器镜像)/ `file`(产物,文件或目录)。`pipeline.ArtifactJAR` / `ArtifactDist` 常量保留为**历史别名** —— 校验仍接受(存量流水线与 `.pipewright.yml` 不改也照跑),读取时归一(`pipeline.NormalizeArtifactTier`,设置 `load`/`normalizeBuild` + 抽屉 `splitOnType`)到 `file`,下次保存自然落库。折算不变:`EffectiveJobType` 把 image 档折 `build_image`、其余折 `script`;**运行期产物类型契约(`image`/`jar`/`dist`/`archive`)与部署节点的「产物偏好」都没动** —— 后者筛的是运行期类型,不是档位。`Builder.Run`(旧设置驱动路径)的按档位默认命令改为按**构建环境语言**取默认(java → mvn、node → npm、其余 no-op),因为这条路径没有 commands 字段,按档位报错会让它整体失效 |

### 3.3 未实现项原因

#### 原因 1/2/3(已消除):阶段 11 + 12 + 20 —— 镜像只有一个来源

**结论**:三处一起落地,链路是「前端只能选目录 → 保存期白名单 → 执行期再解析一次」。

- **单一入口**:`internal/pipeline/buildenv_validate.go` 的 `BuildEnvSnapshot.ResolveJobEnv` 是唯一求值点;
  保存期(`enforceBuildEnvCatalog`)与执行期(`internal/build/buildenv_runtime.go`)共用它,规则不会两处漂移。
- **优先级**:`buildEnvId` → `image`/渲染后镜像(必须在目录内) → `toolchainLanguage`+`toolchainVersion`。
- **不做迁移**:旧配置里手填的镜像若不在目录内,保存 422 / 运行期直接失败并提示「请重新选择构建环境」。
  这是刻意的:静默改写用户流水线比报错更糟。
- **模板节点**:保留 `{{参数}}`,但参数域 = 目录;渲染后二次校验(`off_catalog` 拒绝)。
- **拉取凭据**:环境绑定的 registry 凭据经 `--password-stdin` 注入,不进 argv/日志;登录失败只记一行、
  不判失败(镜像可能已缓存)。
- **域中立**:`internal/pipeline` 不 import buildenv/configprofile;由 `internal/httpapi/buildenv_gate.go`
  适配成 `pipeline.BuildEnvGate` 注入 main.go。目录快照**不缓存**,管理员刚禁用的环境不会被正在跑的构建用上。

**历史背景**(为什么当时没做):当时在无 docker 的沙箱里,改 build 包无法联调;本轮在有 docker 的本机跑通了。

#### 原因 4(已消除):credentials 表 owner_id/enabled 未落地

**曾经的原因**:v6.2 阶段 1 早期尝试过 `0053_credentials_owner.sql`,给 credentials 加 owner_id/enabled/description 等列 + scope/owner CHECK 约束,**导致 25+ 单测的 `INSERT INTO credentials` 头部被破坏**(legacy 单测 helper 写死 8 列 INSERT,新 CHECK 约束报错),为不阻塞主线而撤销迁移。
**现在**:分组权限 P1 以 `0058_credential_owner` 重做——列全部落地,`ListWithActor` 按 actor 过滤,`setEnabledWithActor` 真写 `enabled`。scope/owner 的 CHECK 换成 Go 侧写入前校验(SQLite 不能对已有表补 CHECK)。原「待你决策 A/B」作废。

#### 原因 5:邀请注册流(C2)未做

**直接原因**:计划里"完整用户管理"是阶段 17 后的独立 story(计划 §九 注释提到 "完整用户管理(邀请注册/启用禁用)是后续 story")。
**现状**:`/api/admin/users` 列表已通(阶段 9),但**没有邀请端点**(`POST /api/admin/users/invitations`、`POST /api/auth/register`)。
**联调 workaround**:用 `cmd/tmp-mkuser/main.go` 临时程序 + `auth.HashPassword` 直接 INSERT 一条普通用户(alice)进 users 表。
**后续**:独立 story。

#### 原因 6(已消除):ConfigInjector 拷贝进容器(C4)

**结论**:已做,但实现形态与计划里的 `runner.ConfigInjector` 不同 —— 走 `-v 宿主文件:容器目标路径` 挂载而非 `docker cp`:
一次 `docker run` 内完成,不需要先起容器再拷,也不会把配置内容写进 argv/日志。
**真机证据**:容器内 `wc -c /root/.npmrc` → 90 字节(见 MANUAL-VERIFICATION §2 A5b)。
**入口约束**:job 只能引用 `configProfileIds`(目录 ID 串),语言不匹配/已禁用/路径非法在保存期就被拒(§2.8)。
