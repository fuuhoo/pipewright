# 版本发布流程

> 这份文档是发版的**执行清单**:每一步都给命令和判据,照着走完就是一次完整发布。
> 判据一律写「看什么才算过」,不看流水线绿灯本身 —— 绿灯只说明它自己那一步成功。
>
> 最近一次照此走完的是 v0.17.0(2026-10-29,反代配置落卷/重新下发 + 变量组多分组 + 构建阶段按需添加 +
> 环境入口隐藏):五条 run 一次全绿,1 个迁移 ×2 方言(0088_variable_group_groups)。
> 这一版迁移**只有建表 + 建索引**,没有改列/回填/删列,不存在破坏性升级。
> 耗时:ci(tag) 3m18s / release 5m19s / aliyun-image 3m58s / **caddy-image 14m39s(仍最慢)** / ci(master) 2m27s。
> 更早照此走完的是 v0.16.0(2026-10-29,服务器多分组 + OAuth 初始口令 + 反代镜像可配置/自动推送 +
> 纯发布项目 + 复制文件夹):`release` / `aliyun-image` / `caddy-image` / `ci`(tag push)四条绿
> (4m20s / 4m38s / **21m08s caddy-image 还是最慢** / 3m10s),`ci`(master push)那条红在 backend 测试,
> 但同一 commit 的 tag `ci` 与本地 `go test -count=1 ./...` 都绿 —— 判据仍以第 7 步的硬证据为准,
> 偶发红别急着改代码,先按第 6 步换 token 拉日志定位(这次 PAT 仍是 401,拿不到日志,只能靠重跑)。
> v0.16.0 **有 3 个迁移 ×2 方言(0085_proxy_config / 0086_users_local_password / 0087_server_groups)**:
> 0085 只建表 + 幂等 INSERT,0086 是 ADD COLUMN + 回填 UPDATE,**0087 会 `DROP COLUMN servers.group_id`(升级前备份)**。
> 更早照此走完的是 v0.15.0(2026-10-29,一人多角色 + 建组功能点 + 状态页指标后台采样 + 穿梭框统一):
> 五条 run 一次全绿,1 个迁移 ×2 方言(0084_user_roles)。
> 再往前是 v0.13.0(2026-10-27,通知投递落到台账页 + 复用库模板可编辑),1 个迁移 ×2 方言(0083)。
> 上一版 v0.12.0(2026-10-24)是构建现场快照 + 运行保留两件事的功能版,4 个迁移(0079–0082);
> v0.10.0(2026-10-22)的 `ci`(tag push)当时红在我自己新加的 CLI 测试上 —— 见文末附录的「发版实况」。
>
> **记号约定**:`<ver>` 指不带前导 `v` 的三段版本(如 `0.6.0`)。git tag 与 GitHub Release 用 `v<ver>`,
> 镜像标签与 Release 资产名用 `<ver>`(`aliyun-image.yml` 里 `${version#v}` 就是去掉那个 `v`)。
> 踩过一次:对着 ACR 写 `:v0.8.0` 会得到 `no such manifest` —— 那是拼错了,不是没发出去。

## 0. 一页速览

| 步 | 做什么 | 通过判据 | 耗时 |
|---|---|---|---|
| 1 | 本地全量验证 | fmt/vet/test 全绿,前端 typecheck + 单测 + build 全绿,二进制 `/version` 不是 `dev` | ~5min |
| 2 | 按功能分提交 | `git status` 干净,运行时数据一个都没进暂存区 | ~10min |
| 3 | 定版本号 | 语义化:破坏性 → major,新功能 → minor,只修 bug → patch | 1min |
| 4 | 推 master | 远端 sha == 本地 sha | <1min |
| 5 | 打 tag 并推 tag | `git ls-remote --tags` 能看见 `refs/tags/v<ver>` | <1min |
| 6 | 盯四条 workflow | 四条 run 的 conclusion 都是 success | ~30–45min(ACR 跨境是瓶颈) |
| 7 | 发版终检 | Release 资产可下载 + ACR 四标签存在 + 镜像自述版本对 + latest 已切 | ~10min |
| 8 | 发布后收尾 | README 示例版本、构建环境目录、文档都跟上新版 | ~10min |

第 5 步一推 tag,`release`(GitHub Release + ghcr)、`aliyun-image`(ACR)、`caddy-image`(随车 Caddy)
三条同时开跑,`ci` 也会因为 tag 推送上跑一遍 —— 这四条都是 push/tag 触发,没有人工审批步骤,
所以**推 tag 之前必须先把 1–4 做完**。

## 1. 本地全量验证

在仓库根目录:

```bash
make fmt-check          # 等价于 CI backend job 的第一步 gofmt -l cmd internal embed.go
make vet
make test
GOTOOLCHAIN=local GOPROXY=https://goproxy.cn,direct make go-build   # 必须带 ldflags,否则 /version 报 dev
```

前端(改过 `web/src` 才需要,但发版一律建议跑满):

```bash
cd web
npm run typecheck        # vue-tsc --noEmit
npm run test             # vitest run,含 i18n 三网关:keyParity / componentKeys / messageCompile
npm run build
```

判据与注意:

- **别用 `go build` 直接编**:`make go-build` 才注入 `-ldflags`,少了它 `/version` 返回 `dev`,
  发出去的镜像自述版本就是错的。
- **别在 `web/` 跑 `npm run format`(prettier)**:本仓库没有 prettier 配置,跑一次会重排整个前端。
- **`make clean` 会删掉 `web/dist`**,而 `web/dist/index.html` 是入库文件(go:embed 需要它存在)。
  发版前不要 clean;真删了就得 `npm run build` 重新生成,别把「index.html 被删」带进提交。
- **改过 `web/src` 就不止跑门禁,要在浏览器里点到新功能**:入口文件名是**内容 hash**,重新打包必变
  (`index-CXX0pfe0.js` → `index-sO79ZZab.js` 就是这样),而 `:8080` / `:8081` 跑的是已嵌入 web 包的旧二进制 ——
  不 `make build` 重新嵌入 + 重启两个实例,界面永远是你改动之前的样子,v0.13.0 就在提交前被这一条卡住过:
  门禁全绿、功能在库里、用户在页面上什么都没看见。**判据是用户的真实账号在新 UI 上点到那条功能,不是绿灯。**
- CI 的门就是这几条:`ci.yml` 的 backend(gofmt → vet → test → 静态 build)、frontend(build)、
  mem-budget(常驻内存 ≤100MB,`scripts/mem-check.sh`)。本地全绿不代表 CI 绿,但本地红一定 CI 红。

## 2. 按功能分提交

纪律:

- **一条提交一个功能**,不要 `git add -A` / `git add .`。按路径点名 add,提交完 `git status` 复核
  暂存了什么。
- 每条中间提交都要能独立通过检查:纯逻辑 lib 先于消费它的页面提交,后端先于前端;Go 提交跑
  `make fmt-check vet test`(可只跑受影响的包),前端提交至少跑 `npm run typecheck` 和受影响的
  `vitest`。想严格验中间提交,开一个临时 worktree 逐条 checkout:

  ```bash
  git worktree add --detach /tmp/pwck <sha>
  ln -s "$PWD/web/node_modules" /tmp/pwck/web/node_modules   # 省一次 npm ci
  # 提交消息里引用 file:line 前先核对行号还在
  ```

- **绝不入库的运行时数据**(仓库根,`.gitignore` 已覆盖,提交前还是要用眼过一遍):
  `pipewright.db`、`master.key`、`data/`、`repos/`(私有源码镜像!)、`artifacts/`、`cache/`、
  `project-cache/`、`bin/`。新增同类目录就顺手补 `.gitignore`,别靠force-add。
- 提交消息风格:中文 subject + `feat(scope):` / `fix(scope):` / `docs:` 前缀,正文写**为什么**
  (约束、踩过的坑、为什么不选另一条路),不写流水账;不加 `Co-authored-by`。

## 3. 定版本号

真源是 **git tag**:`.goreleaser.yaml` 用 tag 定 `{{ .Version }}`,`aliyun-image.yml` 用
`git describe` 去前导 `v`,二进制的 `-X …/internal/version.Version` 也由它注入。代码里没有需要
手改的版本常量,README 里的示例版本是**文档**,发完再对齐(见第 8 步)。

选档:

| 变化 | 档 | 例子 |
|---|---|---|
| 只修 bug / 文案 | patch | v0.10.0 → **v0.10.1** |
| 新功能,接口与数据向后兼容 | minor | v0.11.0 → **v0.12.0** |
| 破坏性(接口/数据格式/默认行为改了,老库不能直接升) | major | v0.x → v1.0.0 |

想先探一枪再正式发,可以发 `v0.6.0-rc.1`:两条流水线都会把它标成 prerelease,且
**不覆盖 `latest` / `latest-docker`**(见 `aliyun-image.yml` 的 `is_stable` 判定)。

## 4. 推 master

```bash
git push git@github.com:fuuhoo/pipewright.git master:master
```

为什么不是 `git push origin master`:`origin` 是 HTTPS 地址,而本机没有 GitHub 的 HTTPS 凭据,
`github.com:443` 直连也不通,会停在 `could not read Username`。SSH 那条是通的(`~/.ssh/config` 走
ssh.github.com:443)。同理**不要**为此改用户的 remote URL。

推之前确认能快进,别把别人的提交冲掉。**别用 `git fetch origin` 的结果当依据** —— 2026-10-24 实测它会
`error: RPC failed; curl 16 Error in the HTTP2 framing layer`,fetch 失败后 `master..origin/master` 是空的,
看着像「远端不比我新」,其实是一个都没拿到。改用 SSH 侧的直接对账:

```bash
git ls-remote git@github.com:fuuhoo/pipewright.git master   # 远端真实 sha(本地 origin/* ref 可能是旧的)
git merge-base --is-ancestor <上面的 sha> HEAD && echo 可快进
```

推送本身会触发一次 `ci`(它是无过滤 `on: push`)。如果这一批提交里还没有要发布的内容,又不想跑
CI,把 `[skip ci]` 放进**本次推送的最后一条**提交信息(GitHub 对 push 事件只看 tip)。改信息用
`git commit --amend -m`,改完 `git diff HEAD@{1} HEAD` 必须是空。

## 5. 打 tag 并推送

```bash
git tag -a v<ver> -m "v<ver>: <这一版的一句话主题>"
git push git@github.com:fuuhoo/pipewright.git v<ver>
```

- tag 用 **annotated**(`-a`),changelog 和 `git describe` 都依赖它;历史 tag(v0.5.x)都是 annotated。
- **tag 一推就真发出去了**:GitHub Release 立刻公开(`.goreleaser.yaml` 里 `release.draft: false`),ACR 的
  `latest` 也跟着切。这一步和第 4 步一样,属于要用户明确点头的动作。
- 版本号必须写成规范三段(`X.Y.Z`),工作流里有正则门;`git describe` 在无 tag 仓库会退化成短 SHA,
  所以别指望它兜底。

## 6. 盯四条 workflow

本机 `api.github.com` 可达(`github.com` 不通,两者不矛盾),用 PAT 查(读法:`Authorization: Bearer`,
**绝不打印 token 值**):

```bash
PAT=$(tr -d '\r\n' < ~/github/pat.txt)   # 只当变量用,别 echo
SHA=$(git rev-parse HEAD)
q() { curl -s -H "Authorization: Bearer $PAT" "https://api.github.com/repos/fuuhoo/pipewright$1"; }

# 看这个 commit 上跑了几条(推 master + 推 tag 各触发一次 ci,所以正常是 5 条 run)
q "/actions/runs?head_sha=$SHA&per_page=20" \
  | jq -r '.workflow_runs[]|"\(.name)\t\(.status)\t\(.conclusion // "-")\trun \(.run_number)"'
# 逐 job / 逐 step 定位失败点
q "/actions/runs/<run_id>/jobs" | jq -r '.jobs[]|"\(.name)\t\(.conclusion)\t\([.steps[]|select(.conclusion=="failure")|.name]|join(","))"'
```

四个已知的坑:

- **`/actions/commits/<sha>/actions-workflows` 在这个仓库返回 404**(2026-10-13 实测),用上面
  `runs?head_sha=` 那条;别把它当成「流水线没起来」。
- **跑动中的 job 取不到部分日志**:`/actions/jobs/{id}/logs` 在 job 结束前返回 404(`BlobNotFound`),
  不是日志被删,等它 completed 再拉。
- **job 日志会 302 到 Azure blob**:带着 Bearer 跟进重定向会 401,要先拿 `Location` 再**不带** Authorization 请求。
- **匿名调 release 接口会被限流**:`GET /releases/latest` 返回的 JSON 里没有 `tag_name`(KeyError,不是网络问题),带 token 才正常。
- **PAT 过期时 `runs?head_sha=` 仍可匿名查**(仓库公开,先试匿名再怀疑流水线没起来);但 `jobs/{id}/logs`
  匿名必 403,拿日志必须有有效 token。2026-10-29 实测 `~/github/pat.txt` 里那条已是 `Bad credentials`,
  该次发版改用匿名 runs 接口 + `docker buildx imagetools inspect`(本机 ACR 登录仍有效)取证。

耗时波动很大,别拿「哪条是瓶颈」当判据,该看的是每条 run 的 `created_at`/`updated_at` 和逐 job 时间。
历史上 `aliyun-image` 跨境推到青岛**单层 8~13min**、整条 30~45min;v0.12.0 这次基座层在 ACR 已存在、
二进制层只有几十 MB,整条只用了 3m52s,`release` 4m31s、两条 `ci` 各 4min 上下,而 `caddy-image` 19m36s
成了最慢的一条。已经传上去的层会被复用,所以重试时 push 本身快。

## 7. 发版终检(比绿灯更硬)

```bash
# a) GitHub Release 真的存在且有资产(带 token,免得限流假象)
q "/releases/tags/v<ver>" | jq -r '.tag_name, .draft, .prerelease, (.assets[].name)'
# 期望:draft=false,资产 7 个 = 四个平台的 tar.gz + 两个 windows 的 zip + checksums.txt

# b) ACR 四个标签都到位。**首选证据是 aliyun-image 的 manifest job 日志** —— 仓库私有,
#    匿名 `docker manifest inspect` 必是 `denied`,那不代表没发出去;而登录要用户自己做。
q "/actions/runs/<aliyun-image 的 run_id>/jobs" | jq -r '.jobs[]|select(.name=="manifest")|.id'
# 拿到 job id 后按第 6 步那条「先取 Location、再不带 Authorization」的方法拉日志,看四类 pushing 行:
#   …/pipewright:<ver>          ← sha256:A
#   …/pipewright:<ver>-docker   ← sha256:B
#   …/pipewright:latest         ← sha256:A   (与 <ver> 同 digest 才算 latest 切了)
#   …/pipewright:latest-docker  ← sha256:B
# 末行还该有「已更新 latest / latest-docker」。
# 用户已 docker login 时才能用这两条直接复核架构:
docker manifest inspect registry.cn-qingdao.aliyuncs.com/fubin/pipewright:<ver> | jq -r '.manifests[].platform.architecture'
docker manifest inspect registry.cn-qingdao.aliyuncs.com/fubin/pipewright:<ver>-docker | jq -r '.manifests[].platform.architecture'
# 期望:两条都列出 amd64 + arm64

# c) 镜像自述版本 = 注入到位,而且跑得起来。ghcr 是公开档,不用等 ACR 登录就能验同一个二进制:
docker run --rm --entrypoint /pipewright ghcr.io/fuuhoo/pipewright:<ver> --version
# 期望输出版本号 = <ver>,且 commit = 打 tag 那条提交(不是 dev)

# d) latest 真的切过去了(比 manifest digest,不是比 tag)
docker manifest inspect ghcr.io/fuuhoo/pipewright:latest | jq -S '.manifests[].digest'
docker manifest inspect ghcr.io/fuuhoo/pipewright:<ver>  | jq -S '.manifests[].digest'
# 两条应相同,且与上一版不同;预发布版这里应该「不一致」—— 它故意不碰 latest
```

再加一条本地抽查:`shasum -a 256 -c checksums.txt` —— 要看到逐行 OK 才算证据,本机 `/sbin/sha256 -c`
只给退出码、一行都不打。资产从 `/releases/tags/v<ver>` 的 `assets[].url`(即 `releases/assets/<id>`)
带着 `Accept: application/octet-stream` 下,2026-10-16 实测直连就通,不用等代理。
解出来的二进制在**空目录**里还要跑一次 `reset-admin-password --generate`:期望退出码 2、报出解析到的
绝对路径,且 `ls` 里不能留下 `.db`(绿灯只说明它自己那一步成功,发布产物本身要单独抽验)。
注意 ghcr 上**没有 `-docker` 档**:带 shell 的运行时只发 ACR,所以上面 b/c/d 用 ghcr 只能覆盖默认档;
要在容器里验 CLI,要么用户 `docker login` 后拉 ACR,要么给 ghcr 默认档加 `--entrypoint /pipewright`
(镜像里它是根目录的 `/pipewright`,不在 PATH 里,直接敲 `pipewright` 会 `not found`)。

## 8. 发布后收尾

- **发布说明里的安装示例要抽验**:界面「检查更新」原样展示 GitHub Release 正文,正文由
  `.goreleaser.yaml` 的 `release.footer` 生成 —— 那里必须写 `{{ .Version }}`(不带 `v`),写成
  `{{ .Tag }}` 就是 `ghcr.io/fuuhoo/pipewright:v0.12.0` 这种**不存在的 tag**,用户照抄必失败。
  发完在本地实例点一次「检查更新」,并 `docker manifest inspect` 一下正文里那条镜像地址。
- **README / README.en.md**:一键安装示例里的 `VERSION=` 或 tag 引用要指向**确实发出去了**的版本
  (v0.5.0 那次只有 ACR 镜像、没有 GitHub Release,示例照写就下载失败)。
- **界面里的「立即更新」**:二进制形态自动下载新版 + 校验 + 替换 + 重启;容器形态只提示
  `docker compose pull && docker compose up -d`(判定靠 `/.dockerenv`,见 `internal/version/selfupdate.go`)。
  发布后在本地测试实例点一次「检查更新」,确认列出的就是新版 —— 检查更新读的是
  `fuuhoo/pipewright` 的 releases/latest。
- **构建环境镜像**:新版内置目录引到的上游镜像要按双架构镜像到 ACR,走
  `scripts/mirror-build-envs.sh`(源默认 docker.m.daocloud.io,`openjdk` 那批要换
  `SRC_BASE=public.ecr.aws/docker/library`)。两个硬约束:
  - **本机 OrbStack 上的镜像全是 arm64-only**,直接 push 会**覆盖掉仓库里已有的双架构 tag**;
    要跨架构就 `--platform linux/amd64` 重拉,或者在 CI/境内机器上做。
  - 别重列 ACR 上已经是完整多架构的 tag(比如 `alpine:latest`),imagetools 只会重建 amd64+arm64,
    再跑一次反而把现有档收窄;连着两次 `imagetools create` 还可能吃 ACR 的 `429 toomanyrequests`。
- 若改了内置目录(`internal/buildenv/seed.go`):`SeedIfEmpty` 按 `(language, version)` 幂等逐条插,
  已存在的组合跳过,所以老库升级后新增条目会自动补上,不用手工导一遍。

## 9. 失败与补发

| 症状 | 原因 | 处置 |
|---|---|---|
| `aliyun-image` 红在 `manifest` / `login` | 境外出口向 `dockerauth-cn-qingdao` 取 OAuth token 被 `connection reset by peer`(GDS 调度) | `POST /actions/runs/<id>/retry` —— 注意这会**重跑整条 workflow**(prepare/frontend/binaries/image 全来一遍,约多 20min),不是只补失败 job;已上传的层会复用所以 push 快 |
| 只想补镜像,不想重跑 release | — | `aliyun-image` 有 `workflow_dispatch`,传 `version`(不带 `v`)与 `push_latest`。**dispatch 的工作流文件必须在默认分支 master 上**,否则 API 404 |
| Release 建错了 / 要下架 | — | `PATCH /repos/.../releases/<id>`,或直接删 tag + 删 release 再重打(删 tag 会影响别人的检出,先确认) |
| 发出去的 tag 想改内容 | — | **不要** move 已推送的 tag。打 patch 版重发(v0.6.0 → v0.6.1) |
| 本地误按 digest 引用镜像 | OrbStack/containerd 的 `docker push` 会把 `unknown/unknown` attestation 一起推成 OCI index,`imagetools create` 按 tag 引用就把它并进多架构清单 | 按**镜像 manifest 的 digest** 引用,或直接在 ACR 侧合并;`aliyun-image.yml` 已经用 `oci-mediatypes=false` + `--provenance=false` 规避 |

## 10. 凭据边界(发版全程适用)

- ACR 的用户名/口令只活在 GitHub Actions Secrets(`ALIYUN_ACR_USERNAME` / `ALIYUN_ACR_PASSWORD`),
  **不进文件、不进日志、不进镜像**,也不由本地代填 —— 需要 `docker login` 时由用户自己执行。
- 本地测试实例的管理员口令、GitLab / Gitee / GitHub 的账号口令一律**不写进这份文档**,也不写进任何

  当时并不存在的文件,于是 `store.Open` 顺手建了空库、迁移把表建齐,命令走「空库建号」那条路给一个从未存在的
  管理员设好口令,末了回一句「已为内置管理员设好口令」成功。正在跑的实例用的还是 `/data/pipewright.db`,
  登录照旧失败,而看的人只会以为这条命令不管用。
  现在开库前先 `os.Stat` 解析到的 sqlite 文件:不在就退出码 2,报错带**绝对路径 + 当前目录 + 两条出路**
  (`cd /data` 或 `PIPEWRIGHT_DB=` 写全)。判据为什么用「文件存不存在」而不是「库里有没有管理员」——
  服务在跑,它用的库必然已经存在;「有文件但还没有管理员」仍是合法的冷启动,照旧放行,
  真要从零建库得显式加 `--create-missing`。mysql 没有文件可 stat,跳过。
- **`--generate` 的字母表去掉易混的 `i`**(5c32a29,上一版的 tag CI 就红在这)。断言从「这一轮的随机样本」
  改钉在字母表常量上 —— 拿随机样本断言,同一个缺陷要靠运气才测得出来。
- **两个 README 补目录口径**:「忘了管理员口令」那节现在直接说清「先在哪个目录跑,决定改的是哪个库」,
  并给出 `sh -c 'cd /data && …'` 与 `-e PIPEWRIGHT_DB=…` 两种写法;顺手把 `PIPEWRIGHT_DB_DSN` 在英文侧
  只写「MySQL DSN」的误导改掉(sqlite 也能用它写文件路径)。
- **迁移**:这一版**零迁移**(`git diff --name-only v0.10.0..v0.10.1 -- internal/store/migrations` 为空),老库直接升。

  SSH 发布到目标机三条线一个台子。三张新表见迁移 0070–0072(证书仓库 / ACME 账户 / 发布落点)。
